# Agent Instructions

This repo has two entry points: an **indexer** (writer) and an **MCP server** (reader). They share a common core and operate on the same Qdrant collections.

## Commands

```bash
COLLECTION=my-docs npm run index <file|folder>  # index documents
npm run mcp                                      # start MCP server (stdio)
npm run sync                                     # sync config.json + ensure indexes
```

## How to search the knowledge base

Use the MCP tools — do not read files from `chunks_out/` directly. MCP tools return live data from Qdrant; `chunks_out/` is a review artifact and may be stale.

**Start with `qdrant_collection_info`** to see what collections exist and how many points they have.

Then use the appropriate tool:

| Goal | Tool |
|------|------|
| Find chunks by topic | `qdrant_search(query, collection)` |
| Find chunks by topic within a file | `qdrant_search(query, collection, source_file=...)` |
| Find chunks with a specific tag | `qdrant_find_by_tag(collection, tag)` |
| Read a specific section of a file | `qdrant_get_chunk(collection, source_file, chunk_index, window=1)` |
| See what a file links to | `qdrant_related(collection, source_file)` |
| See what links to a file | `qdrant_backlinks(collection, source_file)` |

If a task requires understanding the full context around a found chunk (e.g. implementing something based on it), follow up `qdrant_search` with `qdrant_get_chunk(..., window=1)` or `window=2` to retrieve the surrounding chunks. Search returns only the matched chunk; adjacent chunks often contain the setup, definitions, or continuation needed to act on it correctly.

## Payload schema

Every point in Qdrant has this payload:

```json
{
  "text": "raw chunk text",
  "context": "1-2 sentence LLM summary of what this chunk is about",
  "section": "heading this chunk belongs to",
  "source_file": "relative/path/to/file.md",
  "tags": ["tag-one", "tag-two"],
  "links": ["other/file.md"],
  "backlinks": ["file/that/links/here.md"],
  "chunk_index": 0,
  "total_chunks": 12,
  "file_hash": "sha256..."
}
```

`source_file` is relative to `SOURCE_ROOT` (if set) or the folder passed to `npm run index`. Use it to navigate between chunks of the same file.

## Graph files

Semantic links between documents are stored per-collection in `graph.<collection>.json` at the project root. The MCP tools `qdrant_related` and `qdrant_backlinks` read from these files — they do not query Qdrant for links.

Graph files store only file-level link/backlink lists — not chunk text or payload. To read the actual content of a linked file, use `qdrant_search` or `qdrant_get_chunk` after resolving the `source_file` from the graph.

## config.json

`config.json` is auto-generated by `npm run sync` and git-ignored. It stores per-collection metadata:

```json
{
  "collections": {
    "my-docs": {
      "embedModel": "bge-m3",
      "vectorSize": 1024,
      "description": "..."
    }
  }
}
```

The MCP `qdrant_search` tool uses `embedModel` from this file to embed the query — the model must match what was used during indexing. If search returns wrong results, check that the collection's `embedModel` in `config.json` matches `EMBED_MODEL` used when indexing.

## Required Qdrant payload indexes

`source_file` and `tags` must have keyword indexes for filters to work. They are created automatically on new collections. For existing collections: `npm run sync`.

## What not to do

- Do not read `src/core/`, `src/indexer/`, or `src/mcp/` source files to answer questions about indexed documents — use MCP tools instead.
- Do not edit `config.json` manually unless changing `embedModel` or `description` — `vectorSize` comes from Qdrant and must not be changed here.
- Do not run `npm run index` without `COLLECTION` set — it will exit with a usage error.
