# Вступ до семантичного пошуку

Сучасні системи пошуку вже не покладаються виключно на точне збігання ключових слів.
Замість цього вони використовують векторні представлення тексту, що дозволяє знаходити
семантично схожі документи навіть тоді, коли запит і документ не мають жодного спільного
слова. Це особливо корисно для мов із розвиненою морфологією, як-от українська.

## Принципи гібридного пошуку

Гібридний підхід поєднує щільні вектори (dense embeddings) і розріджені вектори (sparse
embeddings). Щільний вектор кодує загальний семантичний зміст речення чи абзацу. Розріджений
вектор зберігає лексичні ознаки — важливість конкретних слів у контексті всього корпусу.
Ранжування результатів виконується за допомогою методу злиття RRF (Reciprocal Rank Fusion),
який об'єднує два рейтинги без нормалізації сирих балів. Це робить систему стійкішою до
варіацій масштабу між різними моделями.

## Токенізація кириличного тексту

Токенізатор BGE-M3 базується на словниковому запасі XLM-RoBERTa з підтримкою понад 100 мов.
Для кириличного тексту середня щільність становить приблизно 2–2,5 символи на токен — суттєво
менше, ніж для ASCII-тексту (≈4 символи на токен). Це означає, що проста евристика `довжина/4`
систематично недооцінює кількість токенів у кириличних абзацах. Наслідок: чанки, які
евристика вважає такими, що відповідають ліміту в 400 токенів, насправді містять 600–800
реальних токенів моделі — значно більше за оптимальне вікно.

## Практичні наслідки для чанкінгу

Якщо система дозволяє чанкам виходити за межу в 512 реальних токенів, якість ембедингу
знижується. Dense-вектор усереднює значення всіх токенів, а при надмірно великому чанку
семантичний сигнал розмивається. Sparse-вектор також страждає: модель BGE-M3 навчена давати
вищі ваги найважливішим термінам, але за умови розумного розміру вхідного тексту.

## Архітектура індексатора

Індексатор semidex складається з кількох фаз обробки. Перша фаза — розбиття файлу на чанки
за допомогою рекурсивного алгоритму, який ділить текст спочатку за подвійними переносами
рядків (абзаци), потім за реченнями й нарешті за словами. Друга фаза — генерація контексту
за допомогою мовної моделі (LLM): для кожного чанку створюється короткий опис, що стає
частиною вхідних даних для ембедингу. Третя фаза — власне ембединг: текст `контекст + чанк`
перетворюється на векторне представлення. Четверта фаза — завантаження точок у Qdrant.

## Мовна підтримка в BGE-M3

Модель BGE-M3 розроблена командою BAAI (Beijing Academy of Artificial Intelligence) і
підтримує більше ніж 100 мов, включаючи більшість слов'янських мов із кириличною писемністю.
Для украйнської мови характерна складна морфологія: відмінювання, дієвідмінювання, численні
словотворчі суфікси. Токенізатор ефективно опрацьовує ці форми завдяки алгоритму SentencePiece,
який навчений на великих багатомовних корпусах.

## Порівняння провайдерів ембедингу

У semidex доступні два провайдери для генерації ембедингів. Перший — Ollama з моделлю bge-m3:
вимагає запущеного Ollama-сервера, генерує лише щільні вектори, а розріджені вектори будуються
евристичним методом `hashed-tf`. Другий — ONNX-провайдер (`ONNX_EMBED=1`): модель запускається
локально через ONNX Runtime, генерує і щільні, і розріджені вектори в одному виклику, не
потребує мережевого підключення під час пошуку. Для україномовних корпусів ONNX-провайдер
забезпечує значно кращу якість розріджених ембедингів, бо нейронні ваги токенів адаптовані
до морфологічної різноманітності мови.

## Налаштування середовища

Для запуску indексатора з ONNX-провайдером потрібно задати змінну оточення `ONNX_EMBED=1`.
Модель завантажується автоматично при першому запуску (~2,3 ГБ) і кешується в директорії
`./models/`. Наступні запуски використовують кеш і не потребують мережевого доступу.
Виконавчий провайдер ONNX Runtime обирається через `ONNX_EXECUTION_PROVIDER`: `cpu` (за
замовчуванням), `dml` (DirectML, рекомендовано для Windows із GPU), `cuda` (для Linux із NVIDIA).

## Приклад коду: завантаження токенізатора

```js
import { env, AutoTokenizer } from '@huggingface/transformers';

env.cacheDir = './models';
const MODEL_ID = 'aapot/bge-m3-onnx';

// Завантажуємо лише токенізатор, без ONNX-сесії.
const tokenizer = await AutoTokenizer.from_pretrained(MODEL_ID);

const encoded = await tokenizer('Привіт, семантичний пошук!', {
  padding: false,
  truncation: true,
  max_length: 8192,
});

console.log('Token count:', encoded.input_ids.dims[1]);
```

## Довгий прозовий розділ для перевірки переповнення

Векторні бази даних відрізняються від традиційних реляційних тим, що зберігають не рядки
таблиць, а векторні точки у багатовимірному просторі. Операція пошуку — це не SQL-запит із
умовами фільтрації, а обчислення близькості між вектором запиту і векторами в базі. Qdrant
реалізує цю операцію через HNSW (Hierarchical Navigable Small World) — алгоритм, що будує
граф наближеності між векторами та дозволяє ефективно знаходити найближчих сусідів навіть
у просторі з тисячами вимірів. Гібридний пошук у Qdrant поєднує щільний і розріджений
вектори через окремий механізм злиття ранжувань, а не через конкатенацію векторів. Це дає
можливість незалежно налаштовувати параметри щільного й розрідженого пошуку — кількість
кандидатів (`prefetch_limit`), коефіцієнт злиття RRF (`RRF_K`), кількість фінальних
результатів. Важлива властивість: оцінка RRF не має абсолютного значення — вона залежить
від кількості кандидатів і параметра злиття. Типовий діапазон оцінок для гібридного пошуку
у semidex становить 0,016–0,033; не варто інтерпретувати нижчу оцінку як нижчу релевантність
без врахування всього контексту ранжування. Ще одна особливість: зміна провайдера ембедингу
(наприклад, перехід з Ollama на ONNX) вимагає повного переіндексування колекції, бо вектори,
отримані різними моделями, несумісні навіть якщо обидві моделі називаються «bge-m3».
