Інструментарій для семантичної індексації та пошуку: обробляє колекції документів у векторну базу даних і надає до них доступ AI-асистентам через MCP. Створено для великих баз знань, які не вміщуються у контекстне вікно LLM.

## Проблема

Великі набори документації (100–150+ сторінок) не вміщуються в контекстне вікно LLM. Передача цілих файлів витрачає токени й знижує якість відповідей. Без структури AI-асистент не може знайти *конкретний абзац*, потрібний для задачі — він або читає все, або вгадує.

## Рішення

semidex обробляє документи у семантично структуровані чанки, що зберігаються у [Qdrant](https://qdrant.tech/). AI з доступом через MCP може отримати лише релевантні чанки для конкретної задачі — точні, контекстно-усвідомлені відповіді без звернення до решти колекції.

## Як це працює

Коли ви запускаєте `npm run index`, semidex обробляє кожен документ через п'ять послідовних фаз. Дві локальні LLM-моделі від Ollama забезпечують інтелект на різних етапах — одна для розуміння мови, інша для представлення змісту.

**Фаза 1 — Chunk (розбиття)**
Документ розбивається на значущі частини. semidex спочатку намагається розбити за заголовками та секціями (структурно-усвідомлений підхід). Якщо секція занадто велика — переходить до розбиття за реченнями з перевіркою меж через LLM, щоб не розривати думку посередині. Результат — набір самодостатніх чанків, кожен із яких охоплює одну ідею або тему.

**Фаза 2 — Contextualize (контекстуалізація)** *(використовує `gemma3:4b`)*
Кожен чанк надсилається локальному LLM із запитом написати 1–2 речення, що описують про що цей чанк *у контексті всього документа*. Це резюме зберігається поруч із текстом чанку. Воно вирішує ключову проблему: чанк на кшталт *«Не повинен перевищувати 512 байт»* позбавлений сенсу без контексту — після контекстуалізації він стає *«Токен сесії в модулі авторизації не повинен перевищувати 512 байт».*

**Фаза 3 — Tag (теґування)** *(використовує `gemma3:4b`)*
Той самий локальний LLM генерує 3–7 семантичних теґів для кожного чанку (наприклад, `["автентифікація", "сесія", "безпека"]`). Теґи обробляються пакетами — N чанків на один LLM-виклик — для швидкості. Вони дозволяють точний фільтрований пошук: знайти всі чанки з теґом `database-schema` по всій колекції.

**Фаза 4 — Embed + Upsert (ембедінг та збереження)** *(використовує `bge-m3` або `snowflake-arctic-embed2`)*
Модель ембедінгів перетворює `context + text` у 1024-вимірний вектор — числове представлення змісту. Схожий контент дає схожі вектори незалежно від точного формулювання. Вектор, теґи, контекст і повний текст зберігаються разом як точка у Qdrant.

**Фаза 5 — Link (лінкування)**
semidex виконує семантичний пошук по всіх проіндексованих колекціях і знаходить top-N найбільш схожих чанків для кожного щойно проіндексованого. Двосторонні посилання та зворотні посилання записуються як у payload Qdrant, так і в локальний файл `graph.<collection>.json`. Це створює навігований граф знань: знайшовши один релевантний чанк, AI може перейти по посиланнях до пов'язаного контенту без додаткового пошуку.

### Чому локальні моделі?

semidex використовує Ollama саме тому, що ваші документи залишаються на вашій машині. Під час індексації жоден текст не надсилається до зовнішніх API — це важливо для власного коду, внутрішньої документації, специфікацій клієнтів або будь-якого контенту, яким ви не можете ділитися зі сторонніми сервісами.

Дві моделі виконують різні ролі:

| Модель | Роль | Використовується у |
|--------|------|-------------------|
| `gemma3:4b` | Розуміння мови — читає текст, пише резюме та теґи | Фазах 2 і 3 |
| `bge-m3` | Семантичне кодування — перетворює текст у вектори для пошуку за схожістю | Фазі 4 та при отриманні через MCP |

Під час запиту (через MCP) та сама модель ембедінгів перетворює пошуковий запит AI у вектор, і Qdrant повертає найближчі збіги — жодного LLM при отриманні, лише векторна математика.

## Сценарії використання

**AI-асистоване виконання проєктів**
Завантажте 150-сторінкове технічне завдання. Попросіть AI реалізувати розділ 3.2. Він запитає базу лише за релевантними архітектурними рішеннями, моделями даних і обмеженнями — і створить код, що відповідає *вашому* проєкту, а не загальному туторіалу.

**Навігація по базі знань**
Проіндексуйте Obsidian-сховище або папку з документацією. AI знаходить зв'язки між документами через семантичні посилання та зворотні посилання — схоже на граф Obsidian, але з можливістю запитів.

**Перехресні посилання між документами**
Фаза лінкування шукає по всіх колекціях. Якщо чанк посилається на концепцію, задокументовану в іншому місці, двостороннє посилання створюється автоматично — AI знає, де шукати далі.

**Інкрементальна переіндексація**
Запустіть повторно після редагування файлів. Переобробляються лише змінені файли (перевірка SHA-256 хешу). Незмінені файли пропускаються за мілісекунди.

## Функції

- **Структурно-усвідомлене розбиття** — враховує заголовки, уникає розривів посередині речення; основний текст, стилізований як заголовок (артефакт Word/pandoc), виявляється та зберігається як контент
- **Контекстні ембедінги** — `context + text` ембедяться разом, не лише сирий текст
- **Пакетні LLM-виклики** — теґування та контекстуалізація виконуються паралельними пакетами; надійний парсер обробляє всі відомі формати виводу gemma3 з коректним відновленням для кожного чанку
- **Пропуск за хешем** — незмінені файли не переобробляються; змінені файли видаляються з Qdrant і переіндексуються чисто
- **Двосторонній граф** — посилання та зворотні посилання між документами підтримуються як у payload Qdrant, так і в `graph.<collection>.json`; застарілі ребра видаляються при переіндексації
- **Стабільна ідентичність документів** — `source_file` зберігається як шлях відносно налаштовуваного `SOURCE_ROOT`; перевіряється на виток за межі кореня на всіх платформах, включно з різними дисками Windows
- **Сумісний з Obsidian вивід** — `chunks_out/` записується після лінкування, тому файли для перегляду містять семантичні посилання; застарілі файли чанків з попередніх запусків очищаються автоматично
- **Індексація папок** — вкажіть на директорію, всі підтримувані типи файлів обробляються рекурсивно, приховані записи пропускаються
- **Лінкування між колекціями** — лінкер шукає по налаштовуваному списку колекцій; несумісні колекції пропускаються з попередженням, а не призводять до збою
- **Шар отримання MCP** — 6 інструментів надають доступ до проіндексованих знань будь-якому MCP-сумісному AI-клієнту
- **Гібридний пошук (dense + sparse)** — кожен пошук комбінує dense семантичні вектори зі sparse лексичними векторами, злитими через Reciprocal Rank Fusion (RRF); автоматично переходить на dense-only для колекцій без sparse підтримки. Sparse encoder обирається per-collection: hashed TF (за замовчуванням) або BGE-M3 ONNX лексичне зважування (`ONNX_EMBED=1`)

## Залежності

### Node.js

Потрібен Node.js 18+. Встановіть через [nvm](https://github.com/nvm-sh/nvm) (Linux/macOS) або [nvm-windows](https://github.com/coreybutler/nvm-windows):

```bash
nvm install 20
nvm use 20
```

### Ollama

Локальний LLM-рантайм для контекстуалізації, теґування та ембедінгів. Встановіть з [ollama.com](https://ollama.com), потім завантажте необхідні моделі:

```bash
# модель ембедінгів (обов'язково)
ollama pull bge-m3

# LLM для контексту та теґів (обов'язково)
ollama pull gemma3:4b

# альтернативна модель ембедінгів (для колекцій лише англійською)
ollama pull snowflake-arctic-embed2
```

### Qdrant

Векторна база даних. Використовуйте безкоштовний рівень [Qdrant Cloud](https://cloud.qdrant.io) (без локального налаштування) або запустіть локально через Docker:

```bash
docker run -d --name qdrant -p 6333:6333 qdrant/qdrant
```

Для Qdrant Cloud: створіть безкоштовний кластер, скопіюйте URL та API-ключ у `.env`.

### pandoc

Потрібен лише для форматів `.docx`, `.odt`, `.rtf`, `.epub`, `.html`:

```bash
# Linux (Debian/Ubuntu)
apt install pandoc

# macOS
brew install pandoc

# Windows
winget install JohnMacFarlane.Pandoc
```

## Довідник провайдерів ембедінгів

Кожна колекція зберігає конфігурацію провайдера в `config.json`. Індексатор і MCP-сервер завжди використовують один провайдер — невідповідність викликає автоматичну переіндексацію.

| `denseProvider` | `sparseProvider` | Dense-модель | Примітки |
|-----------------|-----------------|--------------|----------|
| `ollama` | `hashed-tf` | `bge-m3`, `snowflake-arctic-embed2`, … | За замовчуванням. Потребує запущеного Ollama. Sparse — hashed TF без залежностей. |
| `bge-m3-onnx` | `bge-m3-onnx` | `aapot/bge-m3-onnx` | Встановіть `ONNX_EMBED=1`. Завантажує ~2.3 ГБ один раз. Ollama для ембедінгів не потрібен. Найкраще для українського / багатомовного тексту. |

Змішані комбінації (наприклад, `ollama`+`bge-m3-onnx`) відхиляються на старті.

Всі поточні моделі виробляють вектори розмірністю 1024.

## Налаштування

### 1. Встановлення

```bash
npm install
cp .env.example .env
# заповніть QDRANT_URL, QDRANT_KEY та налаштування моделей
```

### 2. Синхронізація колекцій

```bash
npm run sync
```

Генерує/оновлює `config.json` з ваших реальних колекцій Qdrant і забезпечує наявність необхідних payload-індексів на всіх них. Безпечно запускати повторно в будь-який час.

### 3. Редагування config.json (опційно)

Після синхронізації скоригуйте налаштування провайдера та додайте опис. Дивіться `config.example.json` для всіх варіантів.

```json
{
  "collections": {
    "my-docs": {
      "denseProvider": "ollama",
      "denseModel": "bge-m3",
      "sparseProvider": "hashed-tf",
      "embeddingSchemaVersion": 2,
      "vectorSize": 1024,
      "description": "Документація архітектури проєкту"
    }
  }
}
```

> `config.json` генерується автоматично та ігнорується git. Дивіться `config.example.json` для очікуваної структури.

### 4. Реєстрація MCP-сервера в Claude Code

**Linux / macOS**

```bash
claude mcp add --scope user semidex -- node /absolute/path/to/semidex/src/mcp/server.js
```

**Windows (розширення VS Code)**

Запустіть у терміналі (PowerShell або CMD):

```bash
claude mcp add --scope user semidex -- node C:\absolute\path\to\semidex\src\mcp\server.js
```

Потім натисніть **Reconnect** у панелі MCP (`Claude Code → MCP servers → semidex`). Перезапуск VS Code не потрібен.

Після підключення запустіть `/mcp` у чаті Claude Code для перевірки — сервер відображається як `qdrant` і всі 6 інструментів мають бути доступні:

## Використання

### Індексація

```bash
# проіндексувати один файл
COLLECTION=my-docs npm run index path/to/document.md

# проіндексувати всю папку
COLLECTION=my-docs npm run index path/to/docs/

# повторний запуск — змінені файли переіндексуються, незмінені пропускаються
COLLECTION=my-docs npm run index path/to/docs/

# прив'язати шляхи до кореня сховища для стабільних ID між запусками
SOURCE_ROOT=/path/to/vault COLLECTION=my-docs npm run index /path/to/vault/docs/
```

## Конфігурація

| Змінна | За замовчуванням | Опис |
|--------|-----------------|------|
| `QDRANT_URL` | — | URL інстансу Qdrant |
| `QDRANT_KEY` | — | API-ключ Qdrant |
| `OLLAMA_URL` | `http://localhost:11434` | Базовий URL Ollama |
| `COLLECTION` | — | Цільова колекція (передається на кожен запуск, не в `.env`) |
| `EMBED_MODEL` | `bge-m3` | Dense-модель для Ollama провайдера (якщо `DENSE_PROVIDER` не задано) |
| `CONTEXT_MODEL` | `gemma3:4b` | Модель для контекстуалізації чанків |
| `TAG_MODEL` | `gemma3:4b` | Модель для генерації теґів |
| `VECTOR_SIZE` | `1024` | Повинен відповідати виводу моделі ембедінгів |
| `MAX_CHUNK_TOKENS` | `400` | Максимум токенів на чанк |
| `MIN_CHUNK_TOKENS` | `30` | Мінімум токенів — менші чанки відкидаються |
| `OVERLAP_SENTENCES` | `2` | Перекриття речень між сусідніми чанками |
| `LLM_BATCH_SIZE` | `3` | Чанків на LLM-виклик (теґування + контекст) |
| `LINK_TOP` | `5` | Top-N семантичних сусідів для лінкування |
| `LINK_MIN_SCORE` | `0.75` | Мінімальна косинусна схожість для створення посилання |
| `CHUNKS_OUT_DIR` | `./chunks_out` | Вихідна директорія для `.md` файлів, сумісних з Obsidian |
| `SOURCE_ROOT` | *(цільовий шлях)* | Абсолютний шлях як корінь для ID `source_file`. Встановіть один раз для сховища, щоб ID залишались стабільними незалежно від того, яку підпапку ви індексуєте. Файли за межами цього кореня викликають явну помилку. |
| `LINK_COLLECTIONS` | *(всі колекції)* | Список колекцій Qdrant через кому для пошуку під час лінкування. Рекомендовано, якщо ваш інстанс Qdrant містить колекції з різними моделями ембедінгів або розмірами векторів. |
| `ONNX_EMBED` | `0` | Shorthand: `1` вибирає `denseProvider=bge-m3-onnx, sparseProvider=bge-m3-onnx`. Завантажує ~2.3 ГБ при першому запуску. Ollama для ембедінгів не потрібен. |
| `DENSE_PROVIDER` | — | Явний вибір провайдера: `ollama` або `bge-m3-onnx`. Має пріоритет над `ONNX_EMBED`. |
| `SPARSE_PROVIDER` | — | Явний вибір sparse-провайдера. Повинен утворювати валідну комбінацію з `DENSE_PROVIDER`. |
| `DENSE_MODEL` | — | Перевизначення dense-моделі для `DENSE_PROVIDER=ollama`. Аліас для `EMBED_MODEL`. |

## Необхідні payload-індекси Qdrant

Наступні keyword-індекси повинні існувати на кожній колекції для коректної роботи фільтрів і пропуску за хешем:

| Поле | Тип | Використовується |
|------|-----|-----------------|
| `source_file` | keyword | перевірка хешу, переіндексація, видалення, фільтр `qdrant_search` |
| `tags` | keyword | теґ-фільтр `qdrant_search`, `qdrant_find_by_tag` |

`npm run index` створює їх автоматично для нових колекцій. Для існуючих колекцій запустіть `npm run sync` — ідемпотентно, безпечно для повторного запуску.

## Архітектура векторів

Кожен проіндексований чанк зберігається з двома векторними представленнями:

| Вектор | Тип | Алгоритм | Використовується |
|--------|-----|-----------|-----------------|
| `dense` | 1024-вим. float | Модель ембедінгів (`bge-m3` через Ollama або `aapot/bge-m3-onnx` через ONNX) | семантична схожість, лінкування |
| `sparse` | змінна розмірність | Hashed TF (за замовчуванням) або BGE-M3 ONNX лексичне зважування | keyword-matching |

Під час запиту `qdrant_search` запускає обидва вектори паралельно через Query API Qdrant і об'єднує результати через **Reciprocal Rank Fusion (RRF)**. Це покращує recall для запитів, що поєднують природну мову зі специфічними термінами (назви функцій, змінних, технічний жаргон).

`npm run sync` додає sparse vector підтримку до існуючих колекцій. Нові колекції, створені `npm run index`, включають її автоматично.

**Sparse encoder обирається per-collection** і зберігається в `config.json`. Встановіть `ONNX_EMBED=1` перед індексацією, щоб використовувати BGE-M3 ONNX лексичні ваги (~2.3 ГБ, завантажується один раз). Колекції з різними encoder-ами можуть співіснувати — MCP search обирає encoder автоматично на основі метаданих колекції.

## Ранжування результатів (експериментально)

semidex містить локальний детермінований рерankер, який постобробляє RRF-результати Qdrant перед поверненням їх клієнту. За замовчуванням він **вимкнений** і не додає затримки, коли не використовується.

### Як це працює

При `RERANK_ENABLED=1` MCP-сервер отримує `top × RERANK_PREFETCH_MULT` кандидатів з Qdrant (за замовчуванням: у 4 рази більше, ніж запитано), оцінює їх локально, а потім повертає найкращі `top` результатів.

Оцінювання відбувається у два етапи:

1. **Базовий бал** — `1 / (rank + 1)` з оригінального RRF-рангу. Не залежить від провайдера; не змішує шкали з сирими балами Qdrant.
2. **Буст-сигнали** — детерміновані сигнали поверх базового балу:

| Сигнал | Буст за замовч. | Опис |
|--------|----------------|------|
| токен у `source_file` | 0.08 | Токени запиту знайдено в імені файлу чанку |
| токен у `section` | 0.06 | Токени запиту знайдено в заголовку секції |
| токен у `tags` | 0.05 | Токени запиту знайдено в будь-якому теґу |
| токен у `text` | 0.01 | Токени запиту знайдено в тілі чанку (шумний — зменшений) |
| кількість backlinks | 0.04/посилання | Файли з більшою кількістю вхідних посилань ранжуються вище |

Технічні токени (`snake_case`, `АКРОНІМ`, `camelCase`, довжина ≥ 8) отримують **у 3 рази вищий** бал, ніж прозові слова. Поширені українські та англійські стоп-слова виключені з усіх бустів.

**Жадібний прохід різноманітності** застосовує штраф щоразу, коли вибирається черговий чанк із файлу, який вже є у результатах (незалежно від позиції) — для більш різноманітних результатів.

**Захист top-1** (`RERANK_PROTECT_TOP1_DELTA=0.05`): рерankер витісняє оригінальний RRF rank-0 результат лише тоді, коли перевага конкурента перевищує цей поріг — запобігає деградації найвпевненішого RRF-результату через агресивне ранжування.

### Результати бенчмарку

| Провайдер | Recall@1 (без rerank) | Recall@1 (rerank v2) | MRR |
|-----------|----------------------|--------------------|-----|
| `ollama + hashed-tf` | 90% | 90% | 0.938 |
| `bge-m3-onnx` | 95% | **100%** | **1.000** |

Reranking є **opt-in і нейтральним** на поточному бенчмарк-корпусі (20 запитів, 4 фікстури): 0pp Recall@1 і 0 MRR delta для обох провайдерів при вимірюванні на одному index. Корисний кандидат для більших або більш неоднозначних корпусів, де довіра RRF нижча. `RERANK_ENABLED=0` — правильне значення за замовчуванням.

### Конфігурація

| Змінна | За замовч. | Опис |
|--------|-----------|------|
| `RERANK_ENABLED` | `0` | `1` для увімкнення rerankингу в MCP search |
| `RERANK_PREFETCH_MULT` | `4` | Множник кандидатів: отримати `top × N` з Qdrant перед ранжуванням |
| `RERANK_DEBUG` | `0` | `1` для виведення деталей оцінювання кожного результату в stderr |
| `RERANK_BOOST_SOURCE_FILE` | `0.08` | Буст за збіг токена в `source_file` |
| `RERANK_BOOST_SECTION` | `0.06` | Буст за збіг токена в `section` |
| `RERANK_BOOST_TAGS` | `0.05` | Буст за збіг токена в `tags` |
| `RERANK_BOOST_TEXT` | `0.01` | Буст за збіг токена в `text` |
| `RERANK_BOOST_BACKLINK` | `0.04` | Буст за кожне вхідне backlink-посилання |
| `RERANK_PROTECT_TOP1_DELTA` | `0.05` | Мінімальна перевага балу для витіснення оригінального RRF rank-0 |

### Приклад opt-in налаштування

Щоб спробувати reranking на власному корпусі:

```bash
ONNX_EMBED=1
RERANK_ENABLED=1
RERANK_PREFETCH_MULT=4   # за замовчуванням
```

Запустіть `npm run bench:retrieval:rerank` після увімкнення, щоб переконатися, що reranking допомагає на ваших даних.

## Вирішення проблем

**`fetch failed` під час пошуку**
Ollama має бути запущена, коли MCP-сервер обробляє пошукові запити — вона перетворює запит у вектор перед зверненням до Qdrant. Запустіть Ollama і перепідключіть MCP-сервер.

## Відомі обмеження

**Очищення `chunks_out/`** використовує зіставлення за шаблоном імені файлу (`base__chunk*.md`). Якщо ви вручну створите директорію з іменем, що відповідає цьому шаблону, `rmSync` завершиться з помилкою. Це стосується лише штучно створених крайніх випадків у вихідній папці і не впливає на індексацію чи Qdrant.
