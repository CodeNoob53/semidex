> «отримання заголовків відповіді = сервер ще нічого не генерував» у
> первісному тексті розділу 2 — **невірне**: заголовки позначають лише
> клієнтський момент «байтів ще нема / вже є», а не серверний стан до
> нього.

> підпадає). `index.js`'s `runWithRetry()` тепер приймає предикат
> ЯВНИМ параметром (`search()` передає `isRetryablePreStreamSearch`,

> за назвою операції всередині спільної функції. Розділ 2 нижче лишено як
> є з позначками **[ВИПРАВЛЕНО]** на невірних твердженнях, а не переписано

> drop retries askV1()» на тест «pre-header socket drop = рівно ОДИН Ask-

## Загальний вердикт

Це дуже сильний SDK для свого розміру. Архітектурні рішення (zero-dependency,
injected fetch, «point of no return» для retry, один типізований клас помилки)
прийняті свідомо, задокументовані в коді й покриті тестами, які перевіряють клієнт
проти *реальних* серверних роутів, а не проти фейку, що «випадково згоден» з
клієнтом. Знайдені проблеми — не багі, а переважно контрактні шорсткості та борги,
які почнуть боліти саме тоді, коли роадмап рухатиметься далі (research API,
embeddable chat, indexing examples).

## Що добре

**1. Безпекова постава — зразкова.** Origin піниться один раз на конструюванні;
кожен URL будується конкатенацією з фіксованим літеральним шляхом — жодного
`new URL(userInput, base)`, тобто немає вектора redirect через protocol-relative
специфікатор. `redirect: 'error'` на кожному запиті гарантує, що Authorization і
тіло ніколи не пере-відправляються на Location. Валідація `baseUrl` (заборона
query/fragment/userinfo) і `apiKey` (заборона пробілів, `?&=`, `://`) закриває цілий
клас помилок «вставив креденшл в URL». Помилки конструюються без доступу до ключа
взагалі; `onRetry` отримує лише safe-поля. Це рівень, який рідко бачиш у клієнтах
такого розміру.

**2. Retry-політика продумана до дрібниць.** `attempts: 1` за замовчуванням —
апгрейд пакета ніколи мовчки не множить запити і спенд. Retry лише для
429/502/503/504 (500 свідомо виключений — і це правильно для неідемпотентного Ask).
**[ВИПРАВЛЕНО 2026-08-29: невірно — «Retry лише для 429/502/503/504» описувало
`search()`, а не Ask. До фіксу той самий предикат також ретраїв мережеву
відмову fetch ДО заголовків для Ask, що небезпечно (можливе дублювання
генерації). Тепер Ask має власний, вужчий предикат
(`isRetryablePreStreamAsk()`): мережева помилка ніколи не ретраїться;
ретраїться лише отримане pre-stream JSON-тіло з явним `retryable: true`. Див.
виправлення на початку документа.]**
Головний інваріант — «згенерований стрім ніколи не ретраїться» — enforcement через
`markCommitted()` рівно в момент підтвердження `text/event-stream`, тобто точно на
межі «токени ще не пішли / вже пішли». **[ВИПРАВЛЕНО 2026-08-29: останнє
формулювання вводило в оману — ця межа клієнтська (байти отримані чи ні), а
не доказ того, що сервер ще не почав генерувати ДО неї; саме тому мережева
відмова ДО заголовків тепер ніколи не ретраїться для Ask, незалежно від
того, чи «стрім ще не почався».]** Retry-After поважається, але з ceiling'ом:
якщо сервер просить більше `maxDelayMs`, клієнт віддає помилку з
`retryAfterSeconds` замість безглуздого клампленого сну. Jitter по [half, full]
замість [0, full] — зберігає floor і водночас декорелює флот клієнтів.

**3. SSE-парсер коректний.** Довільні межі чанків, CRLF/LF, keepalive-коментарі
(сервер шле `: keep-alive` кожні 15 с — парсер їх правильно ігнорує), flush
фінального фрейму без trailing blank line, race abort'а проти `reader.read()` з
`reader.cancel()`, flush декодера для multi-byte послідовностей. Малформований JSON
у `data:` — синтетичний `__parse_error__`, який стає типізованою помилкою, а не
мовчазним дропом.

**4. Контракт для споживача чистий.** Один клас помилки на всі режими відмови;
термінальний SSE `error` кидається, а не yield'иться (споживачу не треба перевіряти
`event.type === 'error'`). Невідомі event-типи і поля пропускаються as-is — forward
compatibility за конструкцією. `askText()` знімає з інтегратора ручну акумуляцію
дельт, при цьому `done.answer` авторитетний, дельти — fallback, а стрім без `done`
— типізована помилка `client_incomplete_stream`, а не мовчазний частковий результат.
`retries` як non-enumerable поле — спостережуваність без зміни wire-shape
(`JSON.stringify`/`deepEqual` не ламаються).

**5. Тести правильної форми.** `end-to-end.test.js` ганяє клієнт проти реального
`createLiteApp()` з реальним key store — це анти-дрейф механізм, а не мок, що
підтверджує власні очікування. `fetch-injection.test.js` доводить відсутність
fallback на глобальний fetch, видаляючи його цілком. Retry-тести з інжектованим
random — детерміновані.

**6. Приклади вчать правильної архітектури.** `backend-integration-server.mjs`
демонструє саме те, що потрібно: ключ лише server-side, browser не знає імені
колекції (mapping `assistantId → collection` закритий і серверний), conversation
state — власність бекенда з явним «DEMO ONLY» на in-memory Map. README чесно
позиціонує streaming vs `askText()`.

## Що погано / шорсткості

**П1. `err.requestId` — кореляційний гап на боці Semidex, не універсально мертвий
код (середнє). [ВИПРАВЛЕНО: попереднє формулювання «мертвий код» було неточним.]**
Клієнт читає `X-Request-Id` з двох незалежних джерел — HTTP-заголовка відповіді
й поля `requestId` в error body — і жодне з них само по собі не робить
`err.requestId` мертвим кодом: реверс-проксі перед `semidex-lite serve`
(nginx, Cloudflare, будь-який API gateway) цілком реалістично додає власний
`X-Request-Id` до відповіді, і клієнт коректно його підхопить без жодної зміни.
Гап — саме на боці **Semidex-сервера напряму**: `requestId`
(`src/shared/admin/router.js:113`) сьогодні живе лише в audit-лозі, а
`projectErrorPayload()` в обох контрактах (v1/v2) віддає тільки
`apiVersion/code/message/retryable` — жодного requestId в тілі. Тобто без
проксі перед сервером `err.requestId` сьогодні завжди `null`, і скорелювати
клієнтську помилку з серверним audit-записом напряму неможливо — при тому, що
structured audit logging щойно відвантажений як фіча. Найдешевший фікс —
серверний: віддавати `X-Request-Id` у відповіді (він уже генерується на кожен
запит). Клієнт готовий до цього без змін — це задокументовано в `errors.js` як
намір, і вже сьогодні працює за проксі, що сам додає цей заголовок.

**П2. `timeoutMs` — тотальний бюджет включно зі стрімінгом (низьке, DX-нюанс).
[ВИПРАВЛЕНО: понижено з «середнє» — README вже документував тотальний бюджет,
не бракувало лише явного речення про SSE-стрім.]** Дефолтні 60 с покривають
*весь* виклик: усі retry, backoff і — важливо — все споживання SSE-стріму.
Довга генерація (слабша модель, довга відповідь, повільний провайдер) буде
оборвана посеред стріму з `client_timeout_or_abort`, а `askText()` при цьому
втрачає все, включно з уже отриманими дельтами. Серверний heartbeat кожні 15 с
підтримує з'єднання, але клієнтський таймер активності не бачить. README вже
називав `timeoutMs` тотальним бюджетом реального часу до цього ревʼю — бракувало
лише явного речення, що цей бюджет включає повне читання SSE-потоку, а не тільки
з'єднання. Додано одне речення в README (обидві мови) саме про це; окремий
idle-timeout (що скидався б на кожному фреймі, heartbeat включно) як рантайм-
поведінка свідомо НЕ впроваджується в межах цього виправлення — це залишається
окремою, більшою зміною контракту, якщо колись знадобиться.

**П3. Abort і timeout нерозрізненні, і обидва `retryable: true` (низьке).** Один
код `client_timeout_or_abort` покриває і свідоме скасування користувачем, і
дедлайн. Внутрішній retry-цикл його правильно виключає, але прапорець
`retryable: true` — це порада споживачу, і наївний caller-side цикл «ретраїти все
retryable» повторить запит, який користувач щойно скасував. Розділення на
`client_timeout` (retryable) / `client_abort` (не retryable) було б чеснішим
контрактом. Зараз це зафіксовано тестами, тож зміна — семвер-подія; дешевше
зробити до того, як у клієнта з'являться зовнішні споживачі.

**П4. `AskUnknownEvent` вбивав discriminated-union narrowing у TS — виправлено
(було: низьке, DX). [ВИПРАВЛЕНО: рекомендація `Exclude<string, ...>` з
попередньої версії цього розділу була хибною — прибрана, не залишена поруч.]**
Незалежна перевірка реальним `tsc --strict`-споживачем підтвердила проблему:
з `AskEvent = AskSourcesEvent | ... | AskUnknownEvent`, де `AskUnknownEvent.type:
string`, перевірка `event.type === 'done'` НЕ звужувала тип — `event.answer` і
`event.apiVersion` лишались `unknown` навіть після цієї перевірки, бо
unknown-член (з нелітеральним `type: string`) не виключався з union'у.

Рекомендація попередньої версії цього розділу —
`AskUnknownEvent & { type: Exclude<string, 'sources'|'answer_delta'|'done'> }`
— **недійсна й прибрана**: виключення строкових літералів з `string` у
TypeScript повертає назад `string` (немає типу «string, крім цих трьох
літералів»), тож ця конструкція не звужувала б нічого.

**Реалізоване рішення:** окремі версійні типи подій —
`KnownAskEventV1`/`KnownAskEventV2` (об'єднання лише відомих подій, без
unknown-члена) плюс публічні type guard'и `isKnownAskV1Event()`/
`isKnownAskV2Event()`, що звужують `AskEventV1`/`AskEventV2` до відповідного
`KnownAskEventV*`, виключаючи `AskUnknownEvent`. Після виклику guard'а звичайний
`switch`/`if` на `.type` звужує соundно, бо всі члени, що лишились, мають
літеральний `type`. Two distinct guard-функції (не один перевантажений
`isKnownAskEvent`) — свідомий вибір: `AskUnknownEvent`'s `[key: string]: unknown`
робить `AskEventV1`/`AskEventV2` структурно взаємоприсвоюваними одне одному
через unknown-гілку, тож єдина перевантажена назва могла б обрати не той
overload для деяких входів; дві окремі назви уникають цього повністю. Повністю
soundного рішення все одно немає (виклик «не тієї» guard-функції напряму все ще
структурно проходить через ту саму unknown-гілку) — це задокументовано в
`index.d.ts`, а не приховано. Перевірено strict-фікстурою:
`tests/types/lite-client.types.ts` + `npm run typecheck:lite-client`.

**П5. Не-JSON error body зникає (низьке). [ВИПРАВЛЕНО: попередня рекомендація
показувати сирий сніпет тіла прибрана — тіло проксі може містити внутрішні або
чутливі дані навіть без "секрету" у вузькому сенсі.]** `safeReadJson()` →
`null` → «Request failed with HTTP 502.» Реверс-проксі перед сервером типово
віддає HTML-сторінку; дебажити інтеграцію за таким повідомленням важко. НЕ
рекомендується показувати сирий (навіть обрізаний) сніпет тіла — HTML-сторінка
проксі/балансувальника може розкривати внутрішню топологію, версії, шляхи чи
інші деталі, яких клієнтська бібліотека не повинна пересилати назовні без
контролю. Дешевша й безпечніша діагностика: статус-код, `content-type`
відповіді, і, якщо доступний, `requestId` (див. П1) — цього досить, щоб
відрізнити «проксі віддав щось не-JSON» від «сервер повернув порожнє тіло»,
без ризику витоку.

**Дрібниці, лише зафіксувати.** (а) Валідація `apiKey` забороняє `=` — коректно
для base64url-формату `sdx_v1_*`, але зв'язує клієнтську валідацію з форматом
токена; префікс версії в токені це страхує. (б) `buffer.replace(/\r\n/g)` на
всьому буфері на кожен чанк — потенційно квадратично на патологічному стрімі без
меж фреймів; на практиці обмежено межами фреймів. (в) Три ідентичні catch-блоки
(`SemidexApiError` / aborted / networkError) в `search`/`streamAsk`/зовнішньому
catch — дрібне внутрішнє дублювання. (г) `deepFreeze` результатів — правильний
ownership-контракт, але проксі-бекенд, що декорує події перед ре-емісією, мусить
клонувати; у README про це ні слова.

## Технічні борги, які зростуть (звірено з роадмапом)

**Б1. Рукописний `.d.ts` без жодної автоматичної перевірки — головний борг.
[ВИПРАВЛЕНО: твердження «зараз дрейфу немає» з попередньої версії цього
розділу було невірним — прибрано, не залишено поруч із виправленням.]**
У репозиторії НЕ БУЛО ні прямої/стабільної typecheck-залежності, ні
typecheck-скрипта, ні type-тесту — `336` рядків типів звірялись з `662`
рядками рантайму очима. `typescript` фізично був присутній у дереві (`node_modules/typescript`,
версія `6.0.3`), але лише **транзитивно**, як peer-залежність
`@qdrant/openapi-typescript-fetch` (у `@qdrant/js-client-rest`), автоматично
підтягнута npm — не як явна кореневa devDependency, і без жодного гарантованого
tsc-запуску в тест-сюїті. «Зараз дрейфу немає» було перевіркою ОЧИМА одного
поля (`SearchResult` проти `projectResult()`), а не реальним `tsc --strict`
над клієнтом — і незалежна перевірка реальним `tsc --strict`-споживачем
знайшла підтверджений дрейф у чотирьох місцях:

1. `AskSourcesEvent`/`AskAnswerDeltaEvent`/`AskDoneEvent` декларували
   `apiVersion: 'v1'` безумовно, хоча `askV2()` отримує події з
   `apiVersion: 'v2'` (`src/core/ask-api/v2/contract.js`).
2. v2-поля `conversation.updatedSummary`/`conversation.compactedMessageCount`
   декларувались як обов'язкові й nullable, хоча сервер додає їх умовно через
   spread і ніколи не шле явний `null` (`projectDoneEvent()` в
   `src/core/ask-api/v2/contract.js`).
3. `AskUnknownEvent.type: string` не давав TS звужувати discriminated union:
   після `event.type === 'done'` `event.answer`/`event.apiVersion`
   лишались `unknown` (див. П4).
4. Рекомендація `Exclude<string, 'sources'|'answer_delta'|'done'>` з
   попередньої версії цього розділу була недійсною — виключення літералів з
   `string` повертає `string`, а не звужений тип.

**Реалізовано:** версійно-роздільні типи подій/результатів
(`AskEventV1`/`AskEventV2`, `KnownAskEventV1`/`KnownAskEventV2`,
`AskDoneEventV1`/`AskDoneEventV2`, `AskTextResultV1`/`AskTextResultV2`),
`AskConversationDoneBlock` з опційними (не nullable) `updatedSummary`/
`compactedMessageCount`, публічні guard'и `isKnownAskV1Event()`/
`isKnownAskV2Event()`, і `typescript` як явна кореневa devDependency
(`^6.0.3`, збігається з версією, що вже фізично стояла в дереві). Type-тест
додано: строга `.ts`-фікстура `tests/types/lite-client.types.ts` +
`tests/types/tsconfig.json` (`strict: true`, `noEmit: true`), запускається
через `npm run typecheck:lite-client` і підключена до звичайного `npm test`
через кореневий `pretest`-хук (`package.json`) — тобто виконується автоматично
в CI (`.github/workflows/smoke.yml`, `publish-lite.yml` обидва викликають
`npm test`), не лише вручну. Негативні очікування (`@ts-expect-error`)
перевіряють саме те, що v1 не може мовчки стати v2, і що пропущені
conversation-поля не можна вважати присутніми без перевірки.

**Б2. Версійний skew клієнт↔сервер без політики.** Клієнт жорстко пінить
`/api/v1|v2` — розумно, поки клієнт і сервер їдуть в одному npm-пакеті. Але
роадмап-напрямки (embeddable chat, сторонні бекенди, research API) роблять
реалістичним сценарій «оновлений клієнт проти старого сервера»: сьогодні це
проявиться як 404 без пояснення. Події вже несуть `apiVersion` — гачок є, політики
немає. Коли з'явиться research API (фактично v3-поверхня), варто визначити:
що клієнт робить з 404 на версійованому шляху (окремий code
`server_version_unsupported`?), і чи потрібен capability-discovery ендпоінт.

**Б3. SDK не покриває індексацію — і не може.** Роадмап (P0 demo, «provide
concise JavaScript/TypeScript examples for indexing») передбачає, що зовнішній
застосунок індексує. Але indexing живе на Admin-поверхні, яка навмисно
loopback-only і без автентифікації; bearer-key схема клієнта на неї не поширюється.
Тобто «повний» сценарій демо (зовнішній бекенд, що сам індексує і питає) сьогодні
неможливий через SDK — лише через локальний CLI. Це відомий, чесно задокументований
роадмап-гап (session model для Admin), але варто явно вирішити: або scoped
Integration-ендпоінт індексації під існуючу key-схему (клієнт до цього готовий —
`operations` scope вже існує), або демо офіційно фіксує «індексація — операторська
дія через CLI». Невирішеність тут — борг, який виросте рівно в момент P0-демо.

**Б4. Кореляція помилок з audit-логом (те саме П1, у роадмап-масштабі).** Audit
logging позиціонується як операторська фіча; spend/token ceilings віддають 429 з
Retry-After. Що більше операційних відмов (budget, rate limit, scope), то
болючіша відсутність requestId у відповідях: оператор бачить audit-запис,
інтегратор бачить `err` — зшити їх нічим. Дешево закрити зараз, дорого — коли
з'являться зовнішні інтегратори.

**Б5. Три копії документації контракту. [ЧАСТКОВО ЗАКРИТО: обидва пункти нижче
вирішені в межах цього ж виправлення.]** Контракт подій описаний у: коді
сервера, `.d.ts`, README (плюс приклади). Раніше README-секції клієнта
бракувало явного речення про тотальний timeout для стрімів — тепер додано
(обидва мовні варіанти README). З ростом поверхні синхронізація трьох місць
руками лишається тим самим класом боргу, що Б1; type-тест (`tests/types/`)
тепер закриває саме d.ts-половину цього боргу автоматично — README все ще
синхронізується вручну, і для нього правило «кожна зміна контракту = грін у
e2e-тесті + рядок у README» в AGENTS.md лишається відкритою рекомендацією.
