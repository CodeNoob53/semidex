# Structured security audit logging — design note

Status: **implemented (2026-08-23).** This is the design record for the
audit-event contract and sink introduced by this task. See the roadmap's
"P0. Public-facing hardening" item ("structured security audit logs...")
for how this fits the broader hardening track, and
`docs/security/semidex-lite-public-api-audit-2026-08.md` for the request
pipeline this instruments.

Scope: an instance-scoped audit-event contract and a local JSONL sink that
record security-relevant decisions and administrative mutations for both
Full Semidex and Semidex Lite, without exposing secrets, user content, or
unrestricted filesystem paths. No PostgreSQL or other database dependency is
introduced. No telemetry or network export exists or is planned by this
document.

## 0. Operator quick reference

- **Location:** `SEMIDEX_HOME/audit/audit.log`, one JSON object per line
  (JSONL), UTC timestamps. Full and Lite both write here by default.
  **Two live processes pointed at the same `SEMIDEX_HOME/audit` directory
  at once is not a supported configuration** — concurrent writers and
  rotation between two independent, uncoordinated sinks are unsupported;
  see §9 for exactly what this implementation does and does not attempt to
  guarantee there. Point each concurrently-running instance at its own
  directory via `SEMIDEX_AUDIT_LOG_DIR`, or route both through an external
  aggregation sink, if more than one process must run against the same
  `SEMIDEX_HOME`.
- **Format:** each line has `schemaVersion`, `ts`, `type` (e.g.
  `auth.integration_denied`, `admin.settings_changed`), `outcome`, and a
  small set of allow-listed, type-specific fields — see §2 for the full
  taxonomy. No document text, no Ask questions/answers, no secrets, no raw
  filesystem paths (paths are logged only as a 16-hex-char one-way hash,
  `pathHash`) ever appear — see §3 for the exact privacy rules.
- **Rotation:** size-based, 10 MiB per file by default, 5 files retained
  (active + 4 rotated) by default. Override with
  `SEMIDEX_AUDIT_LOG_MAX_BYTES` / `SEMIDEX_AUDIT_LOG_MAX_FILES`
  (positive integers; an invalid value logs a warning and falls back to
  the default rather than failing startup).
- **Moving the log:** `SEMIDEX_AUDIT_LOG_DIR=/path/to/dir` writes there
  instead of `SEMIDEX_HOME/audit/`.
- **Disabling:** `SEMIDEX_AUDIT_LOG_DISABLED=1` turns the sink into a
  no-op — no directory or file is ever created. Nothing else in Full or
  Lite depends on the audit log existing; disabling it does not change any
  request's outcome, only whether it is recorded.
- **What this is not:** not tamper-evident, not a compliance product, not
  shipped to any external service (no telemetry, no network export — see
  §9 for the full list of limitations). It is a local, best-effort record
  for an operator to inspect on the machine Semidex runs on.

## 1. Why a new module, not an extension of existing logging

The codebase already redacts secrets from three unrelated logging paths
(`sanitiseErrorMessage()` in job logs and the router's catch-all, error
message redaction in Ask/health/generation routes). Those all take an
**arbitrary string** (a caught exception's message, a child process's
stdout line) and try to strip known secret shapes out of it after the fact.
That pattern is explicitly wrong for an audit trail: the task's own
constraint is "event objects must be created from explicit allow-listed
fields; do not log arbitrary request objects, headers, bodies, exceptions,
... and then try to redact them." An audit event is therefore never
constructed from a caught error, a request object, or a settings snapshot —
only from a fixed set of named, typed fields that a call site passes
explicitly. This is a *stricter* contract than the redaction-based logging
that already exists, not a replacement for it; job logs and error redaction
are unchanged.

## 2. Event taxonomy and schema

Module: `src/core/audit/event.js`. Zero dependencies beyond `node:crypto`
(for the one-way path identifier — see §4).

Every event is a frozen plain object with a fixed envelope plus a
per-type allow-list of extra fields. `buildAuditEvent(type, fields)`
constructs and validates one (throws `TypeError` on any unknown field,
missing required field, or wrong-shaped value — this is the
construction-time contract every call site is written against, and is
exercised directly by unit tests). `validateAuditEvent(event)` is the
second, non-throwing check the sink itself runs on whatever it is handed —
see §6 for why both exist.

**Envelope (every event):**

| Field | Type | Notes |
|---|---|---|
| `schemaVersion` | number | `1` today. A future incompatible change bumps this rather than mutating the shape in place. |
| `ts` | string | ISO-8601 UTC, generated by the builder — never caller-supplied, so a call site cannot backdate or omit it. |
| `type` | string | One of `AUDIT_EVENT_TYPE` (below). |
| `outcome` | string | One of a small fixed set (`accepted`, `denied`, `started`, `succeeded`, `failed`, `cancelled`, `requested`, `changed`, `deleted`, `synced`, `created`, `revoked`). |
| `edition` | `'full' \| 'lite' \| null` | Which composition root emitted it, when the caller knows (composition roots pass their own literal; CLI paths that run identically in both editions pass `null`). |
| `requestId` | string or `null` | Per-HTTP-request correlation id, generated once in `router.js` per request (see §5); `null` for events with no originating HTTP request (a job's terminal state, fired from a child-process exit handler well after the response was sent; a CLI key command). |
| `route` | `{ method, path } \| null` | The **registered route template** (e.g. `/api/jobs/index`), never the raw request URL — no query string, no path-param values beyond what a specific event type explicitly allow-lists (e.g. `collection`). |
| `audience` | `'admin' \| 'integration' \| null` | From the matched route's own metadata (`route-audience.js`) — never redeclared. |
| `operation` | string or `null` | Same source as `audience`. |
| `reason` | string or `null` | A short, stable, non-secret reason code for a denial/failure — never a raw exception message. |

**Types** (`AUDIT_EVENT_TYPE`), grouped by the six required-coverage areas:

1. Authentication — `auth.integration_accepted`, `auth.integration_denied`
2. Authorization — `authz.collection_denied`
3. Request protections — `request.host_rejected`, `request.origin_rejected`, `auth.rate_limited`
4. Indexing boundary — `index.root_denied`, `index.job_started`, `index.job_cancel_requested`, `index.job_cancelled`, `index.job_succeeded`, `index.job_failed`
5. Administrative mutations — `admin.settings_changed`, `admin.collection_schema_synced`, `admin.collection_deleted`, `admin.key_created`, `admin.key_revoked`
6. (cross-cutting — see §7 for the Full/Lite composition wiring that makes 1-5 identical in both editions)

Per-type extra fields are declared in one table in `event.js`
(`EVENT_FIELD_SCHEMAS`) so the full allow-list for every event type is
readable in one place rather than scattered across call sites. Examples:
`auth.integration_denied` allows exactly `{ keyId?: string|null, reason:
enum }`; `admin.settings_changed` allows exactly `{ fields: Array<{ key:
enum-of-known-setting-names, action: 'set'|'delete' }> }`.

## 3. Privacy model — what is never logged, and why

Directly from the task's own contract, plus this task's specific
call-site decisions:

- **Never logged, anywhere:** bearer tokens, key digests, the
  `Authorization`/`Cookie` headers, `QDRANT_KEY`/`GEMINI_API_KEY`,
  document/chunk content, Ask question/history/summary/answer text, raw
  provider errors, request/response bodies, and any settings value (old or
  new).
- **Auth denial granularity matches the key store's own, deliberate
  granularity — no finer.** `key-store.js`'s `authenticateToken()` already
  collapses "unknown keyId", "wrong secret", "revoked", and "expired" into
  one internal `AUTH_RESULT.INVALID` outcome, on purpose — see that
  module's own header comment: an unknown keyId still runs a dummy
  constant-time comparison specifically so a caller (and, by extension,
  anything server-side observing only the returned enum) cannot learn
  *which* of those four things was true. The audit event for that path
  therefore records `reason: 'invalid_credential'`, one value for all four
  cases, not four distinguishable reasons. Splitting them apart would
  require adding a second, more detailed signal inside the key store
  purely for audit purposes — a real change to a module whose entire
  design purpose is not leaking that distinction — which is out of scope
  for this task. `not_configured` and `store_unavailable` **are** logged
  distinctly, because the key store already returns them as distinct,
  non-security-sensitive outcomes (no enumeration risk: both mean "no
  usable credential could possibly have worked").
- **Collection names are logged in full, deliberately.** They are
  operator-chosen resource identifiers, already visible throughout the
  running Admin UI, job records, and existing error messages — not secret
  content. An audit log that hashed them would be useless for its actual
  purpose (an operator asking "what happened to collection X"), so they
  are logged as plain strings.
- **Local filesystem paths are never logged in full.** A path can embed a
  local username, an unrelated project name, or other information the
  operator did not choose to expose, and the task explicitly forbids
  "unrestricted filesystem paths." Every indexing-related event instead
  carries `pathHash`: `sha256(canonicalPath)` truncated to 16 hex
  characters (`hashIdentifier()`, `src/core/audit/event.js`). This is
  enough to notice "the same path was targeted repeatedly" (e.g. a
  brute-force scan of the allowed roots) without reconstructing the
  filesystem layout from the log. This is a one-way, unsalted hash — it is
  *not* a secret-safe construction (a small, enumerable set of likely paths
  could be dictionary-matched against it), which is acceptable here because
  the input (a local path) was never confidential in the way a credential
  is; it is a correlation aid, not a confidentiality boundary.
- **Key names are logged.** Like collection names, a key's `name` is an
  operator-assigned label (`key add --name`), not a secret — the digest and
  token are what must never appear, and never do.

## 4. Sink contract and lifecycle

Module: `src/core/audit/sink.js` (the narrow contract + no-op),
`src/core/audit/jsonl-sink.js` (the real implementation),
`src/core/audit/resolve-sink.js` (instance-scoped construction, mirroring
`src/core/auth/resolve-policy.js`'s own pattern exactly).

```
AuditSink = {
  record(event): void        // never throws, never blocks the caller
  flush(): Promise<void>     // resolves once every queued event is durable
  close(): Promise<void>     // flush() + release any resources (timers, fd)
}
```

Two implementations share the same contract:

- **`createNoopAuditSink()`** — every method is a no-op. Used when logging
  is disabled (`SEMIDEX_AUDIT_LOG_DISABLED=1`) and as the router/registry's
  own default when no sink is injected, so every existing test that
  constructs a router/registry without one is unaffected.
- **`createJsonlAuditSink({ dir, ... })`** — the real local sink, used by
  the long-running HTTP server process (both editions). `record()` pushes
  onto a bounded in-memory queue and returns immediately — **no
  synchronous disk I/O on the request path.** A single always-running
  async drain loop (a chained `Promise`, not a `setInterval` — matching
  `rate-limiter.js`'s own "no timers that keep the process alive" rule)
  wakes whenever the queue is non-empty, batches whatever has queued since
  the last drain into one `appendFile`, and goes back to waiting. Backpressure:
  the queue is capped (default 10,000 events); once full, `record()` drops
  the new event and increments a counter instead of growing without bound —
  an audit-logging slowdown must never become a memory leak or a request-path
  stall. A dropped-event count is surfaced through a throttled operator
  warning (see below), never silently.
- **`createSyncJsonlAuditSink({ dir, ... })`** — same file format and
  rotation logic, but `record()` writes synchronously and returns only
  after the line is durable. Used **only** by the `key add`/`key revoke`
  CLI (`src/core/auth/key-cli.js`), which is a one-shot, short-lived
  process: there is no "request path" to protect from blocking, and a
  synchronous write is what guarantees the audit line exists on disk
  before the process exits (an async queue would need an explicit drain
  the CLI would have to remember to await, which is exactly the kind of
  fragile hook the task instructs against). Both variants call the same
  underlying `appendJsonlLine()`/rotation helpers, so the on-disk format
  and rotation behavior are identical either way.

**Format.** One JSON object per line (JSONL), `\n`-terminated,
deterministically key-ordered (`JSON.stringify` over an object built with a
fixed key order, not `Object.keys()` insertion order from caller input) so
two runs of the same event produce byte-identical output — this is what
the "deterministic serialization" unit tests assert. **Newline safety**: no
allow-listed field in any event schema accepts a string that could contain
a literal `\n` (collection names reject `/`/`\` already at the API layer;
`pathHash` is a fixed-length hex string; key/setting names are drawn from
closed enums) — so no escaping trick is needed to keep one event to one
line, and a test proves it by attempting to smuggle a newline through every
string-typed field and asserting the resulting file still has exactly one
line per event.

**Location.** `SEMIDEX_HOME/audit/audit.log` (plus rotated
`audit.log.1`, `audit.log.2`, ...), reusing `env.SEMIDEX_HOME` the same
way `resolve-policy.js`/`key-store.js` do. `SEMIDEX_AUDIT_LOG_DIR` is an
explicit override (mirrors `SEMIDEX_KEY_STORE_PATH`), for an operator who
wants audit logs on a different volume from the rest of `SEMIDEX_HOME`.

**Deliberately no `process.cwd()` fallback (unlike `resolveKeyStorePath()`).**
When neither `SEMIDEX_HOME` nor `SEMIDEX_AUDIT_LOG_DIR` is set,
`resolveAuditSink()` returns a **no-op sink**, not a sink pointed at
`process.cwd()/audit`. A cwd fallback was implemented first, to mirror
`resolveKeyStorePath()`'s own fallback exactly — and was reverted after it
was caught doing real, unwanted disk I/O: `resolveKeyStorePath()`'s
fallback is safe because a constructed-but-idle key store only *reads*
(`existsSync`/`readFileSync`) unless a CLI `key add`/`key revoke` call
explicitly asks it to write, so the hundreds of existing tests that
construct `createApp()`/`createLiteApp()` without knowing about the key
store never touch disk through it. The audit sink is the opposite shape —
`record()` writes on *every* call, driven by ordinary request handling
(a Host check, a 404, a successful auth), not an explicit operator action —
so the same fallback silently created a real `audit/audit.log` in the
**repository root** during `npm test`, because dozens of pre-existing
tests construct a composition root without overriding the (new)
`auditSink` parameter. Caught by `git status` after a full suite run
showing an untracked `audit/` directory, fixed before this task's PR, and
pinned by a regression test
(`tests/unit/core/audit/resolve-sink.test.js`). Real production processes
are unaffected: `admin/bootstrap.js` (Full) and
`packages/lite/bin/semidex-lite.js` (Lite) both call their own
`applySemidexHomeEnv()` before constructing the composition root, so
`SEMIDEX_HOME` is always set by the time `resolveAuditSink()` runs there —
this only changes the ad-hoc/test-construction default.

**Permissions.** The `audit/` directory and every log file are created/
chmod'd `0o700`/`0o600` respectively on POSIX, best-effort on Windows
(`chmodSync` only toggles the read-only attribute there) — the exact
pattern `key-store.js`'s `persist()` already uses, reused rather than
reinvented.

**Rotation and retention.** Size-based: once `audit.log` would exceed
`maxBytes` (default 10 MiB, `SEMIDEX_AUDIT_LOG_MAX_BYTES` override), it is
renamed to `audit.log.1` (shifting any existing `.1`...`.N-1` up by one)
before the next line is appended to a fresh `audit.log`. Retention is a
fixed file count (default 5, `SEMIDEX_AUDIT_LOG_MAX_FILES` override): the
oldest rotated file beyond that count is deleted. Both are checked
lazily, on write, exactly like `key-store.js`'s reload-on-every-call
strategy — no background timer, no started-at-construction cron.
`maxBytes` is a soft cap, not a byte-exact one: the async sink checks the
threshold once per drained BATCH (everything that queued up since the
previous drain iteration), not once per individual event, so a single
large burst can land in one write that pushes the file somewhat past
`maxBytes` before the next batch triggers the next rotation. This is
deliberate — checking and rotating between every event in a batch would
reintroduce per-event synchronous I/O inside the drain loop for no real
accuracy gain at the byte level this setting is meant to operate at (MiB).

**Why env-var overrides, not new `SettingsService` entries.** The task
allows typed settings "only if that matches the existing settings
registry." `ADMIN_ALLOWED_HOSTS`/`ADMIN_ALLOWED_ORIGINS`
(`request-security.js`) and `SEMIDEX_KEY_STORE_PATH`
(`resolve-policy.js`) are the two closest precedents for "operational,
security-adjacent configuration resolved once at composition-root
construction" in this codebase, and **neither** lives in the settings
registry — both are plain env vars read directly, specifically because
they are read once at process start (never mid-request) and are not
something the browser dashboard's Settings UI should expose or let a
same-machine caller flip at runtime. The audit sink's own configuration
(enable/disable, directory, rotation size/count) is the same shape:
operator/deployment configuration, not a runtime-tunable product setting.
Adding it to `definitions.js` would also require Lite allow-list entries
and a Settings UI surface for a feature with no UI-editable analog
today (`ADMIN_ALLOWED_HOSTS` has none either) — out of scope per the task's
own "no ... unrelated refactors" constraint. This is a documented decision,
not an oversight.

**Failure behavior.** A write failure (disk full, permission denied,
`ENOENT` on a deleted `SEMIDEX_HOME`) is caught inside the drain loop /
sync writer and never propagates to the caller — `record()`'s contract is
"never throws." The operator is warned via `console.error`, **throttled**
to at most one warning per 60 seconds regardless of how many writes fail
in that window (a full disk should not itself fill the terminal/systemd
journal with thousands of duplicate lines), and the warning is a fixed,
static string plus the error's `code` — **never** `err.message`, which on a
real Node `fs` error routinely embeds the full, absolute path the sink was
configured to write to (e.g. `ENOENT: no such file or directory, open
'C:\Users\<name>\...'`) — exactly the "unrestricted local path" this whole
module exists to keep out of any log. `code` itself is allow-listed against
a fixed set of known Node `fs` error codes (`safeErrorCode()`,
`jsonl-sink.js`) and falls back to the literal string `unknown_error` for
anything unrecognized, so an unexpected/unusual `code` value cannot smuggle
anything else through either. This is never a recursive call into the audit
sink itself (which is exactly the "no recursive logging" requirement;
logging-about-logging failures always goes to `console.error` directly,
never back through `record()`).

**Shutdown/lifecycle ownership.** `flush()`/`close()` exist on every
`AuditSink` (see the contract above), but only the process that
**constructed** a given sink instance is responsible for calling them — a
handler deep in the request path (`router.js`, `registry.js`, `authorize.js`,
etc.) only ever calls `record()`, never `flush()`/`close()`. For the two
real process entry points, that owner is `src/admin/bootstrap.js` (Full) and
`packages/lite/bin/semidex-lite.js` (Lite, via `startLite()`'s returned
`auditSink`) — each resolves its own sink once (§7) and calls `close()` on
that same reference from its own SIGTERM/SIGINT handler, after `server.close()`'s
callback fires and before `process.exit()`, so every event already queued at
shutdown time is durable before the process actually exits. Both handlers
guard against re-entry (a `shuttingDown` flag) so SIGTERM immediately
followed by SIGINT — or a supervisor sending both — cannot double-close;
`close()` itself is also independently idempotent on every implementation
(`createJsonlAuditSink`'s `closed` flag, `createSyncJsonlAuditSink`/
`createNoopAuditSink`'s already-synchronous no-ops), so calling it twice is
harmless even without the caller-side guard. `close()` is deliberately not
wired into Node's own `server.close()` callback machinery in any surprising
way — it is an ordinary explicit call inside the existing shutdown handler,
not a monkey-patch of `http.Server`'s own close semantics.

## 5. Wiring: request-path events (auth, rate limit, Host/Origin, collection scope)

`src/shared/admin/router.js`'s `handleRequest()` already sits at the one
pre-dispatch chokepoint every request passes through (Host check → Origin/
CSRF check → route match → stage 1 auth → stage 1.5 rate limit → handler).
Rather than thread a new `auditSink` parameter through every
`register*Routes()` function (a change to a dozen call sites), the sink
and a per-request correlation id are added to the **existing** frozen
`auth` context object the router already builds and passes to *every*
handler (admin and integration alike — confirmed by reading
`ask-api/v1/route.js`'s `{ req, res, auth }` destructuring and
`router.js`'s unconditional `await found.handler({ ..., auth })`). Concretely:

- `createRouter({ securityPolicy, integrationPolicy, auditSink })` accepts
  the sink as a fourth optional argument, defaulting to
  `createNoopAuditSink()` — every existing test/call site that constructs a
  router without one is unaffected.
- A `requestId` (`crypto.randomUUID()`) is generated once, at the very top
  of `handleRequest()`, before any check runs.
- The Host check, Origin/CSRF check, stage-1 auth decision, and stage-1.5
  rate-limit decision each emit exactly one event through this sink, at the
  point they already decide accept/deny — no new branch, no new control
  flow, just one `auditSink.record(buildAuditEvent(...))` call alongside
  the existing `return sendError(...)`.
- `auth` gains two more frozen fields: `requestId` and `auditSink` —
  available to every handler, not only integration ones, which is what
  lets `authorize.js`, `jobs.js`, `settings.js`, and `collections.js` emit
  their own events (§6) without their own registration functions gaining a
  new constructor parameter.

`src/core/http/authorize.js`'s `authorizeCollectionAccess()` — stage 2 —
reads `auth.auditSink`/`auth.requestId` and emits
`authz.collection_denied` immediately before throwing
`forbiddenCollection()`, using `auth.route.operation` and the
already-parsed `collection` (the exact value stage 2 evaluates, not a raw
body). No event is emitted on the allow path here — the task's own wording
for this coverage area is "operation/collection-scope **denial**," and
`auth.integration_accepted` (stage 1) already records that a call was
authenticated at all.

## 6. Wiring: indexing, admin mutations

- **`src/shared/admin/api/jobs.js`**: `POST /api/jobs/index`'s existing
  `allowedRootsGuard.checkTarget()` denial now also emits
  `index.root_denied` (via `auth.auditSink`) with `pathHash`, before the
  existing `throw new HttpError(...)` — no change to response behavior,
  ordering, or status codes. `auth.requestId` is threaded one level deeper
  into `registry.startIndexJob({ ..., requestId })` so the job's own
  lifecycle events (below) carry the id of the request that started it.
  `POST /api/jobs/:id/cancel` emits `index.job_cancel_requested` the same
  way.
- **`src/shared/admin/jobs/registry.js`**: `createJobRegistry({
  spawnIndexer, baseEnv, auditSink })` gains a fourth, optional DI
  parameter (default no-op, same convention as everywhere else) —
  instance-scoped exactly like `spawnIndexer`/`baseEnv` already are, so two
  registries built in one process (a Full and a Lite composition root, or
  two tests) never share sink state. `startIndexJob()` emits
  `index.job_started` right after the child process spawns successfully;
  the existing `child.on('exit', ...)` handler emits exactly one of
  `index.job_succeeded` / `index.job_failed` / `index.job_cancelled`
  depending on the same state transition the handler already computes — no
  new state machine, just one `record()` call at the point the state is
  already being decided. This is the one place a job's terminal event is
  emitted from a background callback with no live HTTP request behind it
  (the request that started the job returned 202 long ago), which is
  exactly why `requestId` had to be captured on the job record at start
  time rather than read from a per-request context that no longer exists.
- **`src/shared/admin/api/settings.js`**: after `settingsService.setMany()`
  succeeds (never before — a rejected batch changed nothing and must not
  be logged as if it had), emits one `admin.settings_changed` event with
  `fields: Object.keys(changes).map(key => ({ key, action: changes[key]
  === null ? 'delete' : 'set' }))`. Every `key` is validated against
  `Object.keys(DEFINITIONS)` (`core/settings/definitions.js`'s own
  registry — the same allow-list the service itself enforces) by the event
  schema itself, so a field name can never reach the log file unless it was
  already a real, known setting — this is what "allow-listed field name"
  means concretely. **Never the value**, matching the task's explicit
  instruction.
- **`src/shared/admin/api/collections.js`**: `POST
  /api/collections/:name/sync-schema` and `DELETE
  /api/collections/:name` each emit `admin.collection_schema_synced` /
  `admin.collection_deleted` with the collection name, after the
  operation succeeds (the existing 404-on-missing path is unchanged and
  emits nothing — nothing happened).
- **`src/core/auth/key-cli.js`**: `runKeyCommand()` gains an optional
  `auditSink` DI parameter, defaulting to a **no-op** — this module never
  constructs a real sink itself (a real default would mean every existing
  test calling `runKeyCommand()` without overriding it starts writing real
  files under `SEMIDEX_HOME`/cwd as a side effect, exactly the kind of
  hidden I/O the rest of this codebase's DI conventions avoid). The two
  real CLI entry points construct a real synchronous sink and pass it in
  explicitly, mirroring how each already resolves its own `keyStorePath`
  rather than letting `key-cli.js` guess it: `src/key.js` passes
  `resolveAuditSink({ sync: true, dir: join(semidexHome, 'audit') })`,
  deriving `dir` from the SAME `resolveSemidexHomePaths()` call that
  already produced `keyStorePath` (so the two never disagree when
  `SEMIDEX_HOME` is unset and both would otherwise fall back to their own
  independently-resolved default); `packages/lite/bin/semidex-lite.js`
  passes `resolveAuditSink({ sync: true })` with no override, since
  `applySemidexHomeEnv()` already set `process.env.SEMIDEX_HOME` before the
  CLI's command switch runs, which is all `resolveAuditSink()`'s own
  default resolution needs. `key
  add` emits `admin.key_created` (`keyId`, `keyName`); `key revoke` emits
  `admin.key_revoked` (`keyId`, `keyName`, `status`) for the `revoked` and
  `already_revoked` outcomes (nothing is logged for `not_found` — no key
  was actually revoked). This runs synchronously, in the same process,
  before `runKeyCommand()` returns its exit code — the CLI's `key.js`/
  `semidex-lite.js` call sites are unmodified.

## 7. Composition wiring (Full/Lite parity)

`src/admin/server-full.js`'s `createApp()` and
`src/admin/composition/lite.js`'s `createLiteApp()` each gain one new
resolved value, following the exact pattern `resolvedIntegrationPolicy`/
`resolvedAllowedRootsGuard` already establish in both files: `const
resolvedAuditSink = auditSink ? ensureEditionTag(auditSink, 'full' | 'lite')
: resolveAuditSink({ edition: 'full' | 'lite' })`, passed into both
`createRouter({ ..., auditSink: resolvedAuditSink })` and
`createJobRegistry({ ..., auditSink: resolvedAuditSink })`.
`resolveAuditSink()` (`src/core/audit/resolve-sink.js`) is a plain function
under `src/core/` — staged into the Lite package build like every other
shared `core/` module (it does not touch `local/`, ONNX, Ollama, or any
Full-only import) — so it needs no Lite-specific wrapper the way, say, ONNX
capabilities do.

**`edition` is applied by the sink itself, not by each call site — and by
the COMPOSITION ROOT, not by whatever the caller already did.** Two
functions in `src/core/audit/sink.js` cooperate here: `withEditionTag(sink,
edition)` wraps a base sink so every event `record()`ed through it is
re-emitted with `edition` fixed to that value, overriding whatever
`buildAuditEvent()` defaulted it to (`null` — no call site passes `edition`
itself); `ensureEditionTag(sink, edition)` is what `createApp()`/
`createLiteApp()`/`startLite()` actually call on the `auditSink` a caller
supplies. It does not assume that sink was already produced by
`resolveAuditSink({ edition })` — an ad-hoc/test caller, or a future
integration, may well hand it a plain object that only implements
`record`/`flush`/`close` and knows nothing about editions at all — so it
applies the tag itself whenever the given sink is not already correctly
tagged, and returns the sink unchanged (no redundant wrap) when it already
is. If the given sink is tagged with the WRONG edition (a sink some other
composition root already tagged, whether by accident or as a deliberate
override attempt), `ensureEditionTag()` does not simply wrap around the
outside of it — doing that would silently fail, because `withEditionTag()`'s
`record()` always forwards a MODIFIED event further down the chain, so
whichever wrap sits closest to the real, physical sink is the one whose
`edition` value actually survives; an outer wrap can never override an
inner one this way. `ensureEditionTag()` instead unwraps down to the
original, pre-wrap base sink (tracked on the wrapper itself) and applies
exactly one fresh wrap around THAT, so the composition root's own edition
always wins and at most one wrap layer ever reaches the base sink, however
many times a sink has been re-tagged. This is what makes the "a caller
cannot spoof the opposite edition" and "no needless double wrapping"
requirements both hold at once — see `sink.js`'s own header comments and
`tests/unit/core/audit/sink.test.js` for the mechanism proven in isolation,
and `tests/unit/security/audit-edition-isolation.test.js` for the
composition-root-level proof. The wrapper always builds a new, frozen event
rather than mutating the one it was handed, so a caller-owned event (or a
test's own reused reference) is never touched in place.

**Real production processes own their sink instance explicitly, rather than
relying on the `auditSink ? ensureEditionTag(...) : resolveAuditSink(...)`
fallback inside `createApp()`/`createLiteApp()`.** `src/admin/bootstrap.js`
(Full) and `packages/lite/lite-src/serve-lite.js` (Lite, via `startLite()`)
each call `resolveAuditSink({ edition: ... })` themselves, once, and pass
the result into `createApp()`/`createLiteApp()` as the `auditSink`
argument — this is what lets each process's own graceful-shutdown handler
hold the same reference and call `close()` on it before exiting (§4), and
it is also what fixed a real gap in Lite's own `serve-lite.js`: that file
used to build its own `createJobRegistry()` with no `auditSink` at all,
passed the resulting registry into `createLiteApp({ jobRegistry })`, and
never noticed that doing so bypasses `createLiteApp()`'s own internal
fallback entirely — the router still got a real, resolved sink
(`createLiteApp()`'s own default), but every job-lifecycle event
(`index.job_started`/`_succeeded`/`_failed`/`_cancelled`) was silently
dropped through the no-op default `createJobRegistry()` itself falls back
to. `startLite()` also accepts its own optional `auditSink` override (test
DI only — the real CLI never supplies one) and runs it through
`ensureEditionTag()` itself before sharing it with both `createJobRegistry()`
and `createLiteApp()`, so the value it returns is always the correctly
`'lite'`-tagged wrapper — not necessarily reference-equal to whatever the
caller passed in, but closing it always closes the caller's underlying
sink. `createApp()`/`createLiteApp()`'s own internal `resolveAuditSink()`
fallback still exists and still runs for every ad-hoc/test caller that does
not override `auditSink` at all — only the two real process entry points
bypass it, by supplying their own already-tagged instance up front (which
`ensureEditionTag()` then recognizes as already correct and returns
unchanged, applying no second wrap).

**Same-process multiple composition roots (a test shape, not a documented
production deployment) still each resolve their own sink independently** —
two `createApp()`/`createLiteApp()` calls in one process (or a Full+Lite
pair) get two independent sink instances, each correctly `edition`-tagged
via the mechanism above, and neither shares in-memory queue/rotation state
with the other. If both happen to be pointed at the same
`SEMIDEX_HOME/audit/audit.log` file (the default, unless
`SEMIDEX_AUDIT_LOG_DIR` differs between them), see §9 for exactly what is —
and is not — guaranteed about that. Test-only `createApp()`/`createLiteApp()`
callers that construct many servers per process typically inject their own
fake sink (or rely on the no-op default) exactly like they already do for
`integrationPolicy`.

## 8. Future adapter seam

The `AuditSink` contract (`record`/`flush`/`close`) has no JSONL-specific
shape — a future PostgreSQL (or other) adapter implements the same three
methods and is swapped in at `resolveAuditSink()` without touching
`event.js` or any call site. This task does not build that adapter, add a
database dependency, or add a settings switch to select one; `event.js`'s
allow-listed event objects are exactly what such an adapter would insert
as rows, which is the seam this task was asked to keep open.

## 9. Known limitations

- No cross-process log aggregation: each process instance writes its own
  `SEMIDEX_HOME/audit/audit.log` (or the `SEMIDEX_AUDIT_LOG_DIR` override).
  Multiple replicas behind a load balancer each produce their own file —
  the same limitation the rate limiter's own docs already state for a
  different subsystem, for the same underlying reason (in-process state,
  no shared backend in this phase).
- Not tamper-evident or tamper-proof. A local process with filesystem
  write access to `SEMIDEX_HOME/audit/` can edit or delete the log like
  any other file. No hash-chaining, signing, or WORM storage is
  implemented. This document makes no compliance claim.
- **Concurrent writers and rotation are UNSUPPORTED: two independent sink
  instances appending to the SAME `audit.log` file have no cross-instance
  coordination of any kind, and this implementation makes no guarantee
  about the outcome** — corrected from an earlier draft of this document
  that asserted specific safety properties (no interleaved partial lines,
  no lost events) which this implementation does not actually guarantee.
  This can happen two ways: two composition roots built in one process (a
  test convenience — see §7), or two separate OS processes both pointed at
  the same `SEMIDEX_HOME/audit` directory (**not** a documented or
  supported production deployment). Each sink has its own in-memory queue
  and its own idea of the active file's current size, decided
  independently, with no lock or handshake between them; each write reopens
  the path fresh via `fs.appendFile`/`appendFileSync` rather than holding a
  long-lived file descriptor, and rotation renames the active file out from
  under whoever else is about to write to it. Node's/the OS's exact
  cross-handle and cross-process behavior for that combination (concurrent
  `appendFile`/`appendFileSync` calls from independent file descriptors,
  racing a rename) is not something this implementation tests, controls
  for, or relies on being safe in any particular way — this document does
  **not** claim that concurrent appends cannot interleave into a malformed
  (non-single-line) JSONL record, and does **not** claim that no event can
  be lost. Treat this configuration as unsupported and undefined, not as
  "probably fine." If more than one process must run against the same
  `SEMIDEX_HOME`, point each at its own `SEMIDEX_AUDIT_LOG_DIR` value, or
  route both through an external aggregation sink instead — see the
  operator quick reference (§0) for the same guidance.
- **No distinct "a NEW collection was created" event exists, and none is
  invented here.** Collections are created as a side effect of the spawned
  indexer *child process* — `registry.js`/`jobs.js` never call into Qdrant
  directly, and `kind: 'index'` vs `'reindex'` on `index.job_started` is a
  caller-supplied UI label (design doc §6/registry.js's own comment), not
  something this parent process verifies against Qdrant's actual state
  before the job runs. So today, `index.job_started`/`index.job_succeeded`
  record only "an indexing job targeting collection X started" / "...exited
  0" — truthful and real, but they do **not** truthfully mean "collection X
  was newly created by this run" (it may already have existed). Inventing a
  separate `admin.collection_created` event from information this process
  cannot actually confirm would violate this module's own founding
  contract (§1: never construct an event from anything the call site
  cannot verify). **Follow-up, explicitly out of scope for this task:** a
  truthful `collection_created` event would need to originate inside the
  indexer child process itself (the one place that genuinely knows whether
  it just created a new collection) and be threaded back to the parent —
  e.g. as a new machine-readable line in the child's stdout, parsed by
  `registry.js` the same way `[semidex:progress]` lines already are — not
  fabricated here from information the parent process does not have.
- Auth denial reason granularity is intentionally coarse (§3) — this is a
  design decision inherited from the key store's own anti-enumeration
  contract, not an implementation gap.
