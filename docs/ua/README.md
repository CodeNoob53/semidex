**semidex — це локальна RAG-система для AI-агентів.**

Вона перетворює ваші документи, нотатки, специфікації та знання про код на пошуковий шар пам'яті, до якого AI-асистент може звертатися через MCP. Замість вставки величезних файлів у чат або сподівань, що модель пам'ятає ваш проєкт, semidex зберігає знання у Qdrant, розбиває їх на корисні чанки, збагачує резюме, теґами та посиланнями, і повертає лише ті фрагменти, що важливі для поточного завдання.

Простими словами: semidex допомагає AI знайти потрібний абзац, секцію, команду, параметр конфігурації або пов'язаний документ — ще до того, як він відповідає або редагує код.

## Проблеми, які вирішує semidex

| Проблема | Як semidex її вирішує |
|----------|-----------------------|
| Контекстні вікна занадто малі | Індексує і повертає лише релевантні чанки — великі docs ніколи не потрапляють у вікно цілком |
| AI-агент вгадує, коли бракує контексту | MCP-інструменти дають агенту точний доступ до потрібного фрагмента на вимогу |
| Семантичний пошук пропускає точні терміни | Sparse лексичні вектори знаходять `embedding_schema_version`, `ONNX_EMBED`, env vars, назви функцій |
| Keyword-пошук пропускає сенс | Dense нейронні вектори знаходять перефразовані запити і міжмовні синоніми |
| Чанки без контексту незрозумілі | Кожен чанк зберігає LLM-резюме, що описує його в контексті всього документа |
| Пов'язані документи важко знайти | Семантичний граф пов'язує кожен чанк з найближчими сусідами по всіх колекціях |
| Переіндексація великих корпусів дорога | SHA-256 hash-based skip — незмінені файли ніколи не переобробляються |
| Невідповідність провайдера ламає якість пошуку | Query і index завжди використовують один провайдер; невідповідність викликає автоматичну переіндексацію |
| Локальні/приватні документи мають залишатися локально | Ollama + ONNX + Qdrant — жоден текст не виходить за межі вашої машини |

## Чому це більше, ніж семантичний пошук

Більшість RAG-систем запускають одну модель ембедінгів і на цьому зупиняються. semidex поєднує чотири шари пошуку:

1. **Dense вектори** — нейронні ембедінги передають сенс; перефразовані та міжмовні запити знаходяться.
2. **Sparse вектори** — лексичні ваги знаходять точні технічні терміни, ідентифікатори й рідкісні токени.
3. **RRF fusion** — Reciprocal Rank Fusion об'єднує обидва ранжування так, щоб жоден не домінував.
4. **Reranker** (опційно) — локальний детермінований постпроцесор підвищує результати, де токени запиту збігаються з іменем файлу, заголовком секції або теґами; застосовує прохід різноманітності; захищає топовий RRF-результат від агресивного витіснення.

Dense + sparse + RRF — це **основний шлях пошуку**, а не опція.

## Архітектура

```
Документи (md, pdf, docx, epub, txt, …)
  │
  ├─ [1] Chunk          — структурно-усвідомлено: заголовки → речення → LLM boundary check
  ├─ [2] Contextualize  — LLM пише 1–2 речення резюме кожного чанку в контексті документа
  ├─ [3] Tag            — LLM генерує 3–7 семантичних теґів на чанк (пакетно)
  ├─ [4] Embed + Upsert — dense вектор + sparse вектор → Qdrant named vectors + payload
  └─ [5] Link           — семантичний граф: top-N сусідів між колекціями, двосторонньо
         │
         ▼
    Колекція Qdrant
    (dense · sparse · text · section · tags · context · source_file · graph edges)
         │
         ▼
    MCP-інструменти (search · get chunk · related · backlinks · find by tag · collections)
         │
         ▼
    AI-агент отримує точний контекст
```

Під час запиту MCP-сервер ембедить запит тим самим провайдером, що й при індексації, запускає гібридний пошук у Qdrant, опційно ранжує й повертає найкращі чанки з повним payload-метаданими.

## Швидкий старт

### 1. Передумови

- **Node.js 18+** — встановіть через [nvm](https://github.com/nvm-sh/nvm) або [nvm-windows](https://github.com/coreybutler/nvm-windows)
- **Qdrant** — [Qdrant Cloud](https://cloud.qdrant.io) безкоштовний рівень, або `docker run -d --name qdrant -p 6333:6333 qdrant/qdrant`
- **Провайдер ембедінгів** — Ollama (за замовчуванням) або ONNX (дивіться Рекомендовані режими нижче)

### 2. Встановлення

```bash
npm install
cp .env.example .env
# мінімум: задайте QDRANT_URL і QDRANT_KEY
```

### 3. Запустіть Qdrant і завантажте моделі

```bash
# Ollama (режим за замовчуванням)
ollama pull bge-m3        # dense ембедінги
ollama pull gemma3:4b     # LLM для контексту + теґів

# Або: ONNX-режим — Ollama для ембедінгів не потрібен
# задайте ONNX_EMBED=1 у .env — модель завантажиться один раз (~2.3 ГБ) при першому запуску
```

### 4. Синхронізація та індексація

```bash
npm run sync                                    # ініціалізація config.json
COLLECTION=my-docs npm run index ./docs/        # індексація документів
```

### 5. Реєстрація MCP у Claude Code

**Linux / macOS**
```bash
claude mcp add --scope user semidex -- node /absolute/path/to/semidex/src/mcp/server.js
```

**Windows**
```bash
claude mcp add --scope user semidex -- node C:\absolute\path\to\semidex\src\mcp\server.js
```

Потім натисніть **Reconnect** у `Claude Code → MCP servers → semidex`. Запустіть `/mcp` у чаті для перевірки — сервер відображається як `qdrant` із 6 доступними інструментами:

## MCP-інструменти

Типовий робочий процес агента: **search → get chunk з вікном → follow related / backlinks → filter by tag**.

| Інструмент | Аргументи | Опис |
|------------|-----------|------|
| `qdrant_search` | `query`, `collection`, `top?`, `tags?[]`, `source_file?` | Гібридний пошук (dense + sparse + RRF); теґ-фільтр через OR, поєднаний з source_file через AND |
| `qdrant_collection_info` | — | Список усіх колекцій з кількістю точок, провайдером ембедінгів, описом |
| `qdrant_get_chunk` | `collection`, `source_file`, `chunk_index`, `window?` | Отримати конкретний чанк з опціональним контекстним вікном |
| `qdrant_related` | `collection`, `source_file` | Вихідні семантичні посилання для файлу (з графу) |
| `qdrant_backlinks` | `collection`, `source_file` | Вхідні посилання для файлу (з графу) |
| `qdrant_find_by_tag` | `collection`, `tag`, `limit?` | Всі чанки з відповідним теґом, згруповані за файлом |

## Пайплайн індексатора

При запуску `npm run index` кожен документ проходить п'ять фаз:

**Фаза 1 — Chunk (розбиття)**
Структурно-усвідомлене розбиття: спочатку заголовки та секції; розбиття за реченнями з LLM boundary check як запасний варіант. Основний текст, стилізований як заголовок (артефакт Word/pandoc), виявляється і зберігається як контент. Результат: самодостатні чанки, кожен охоплює одну ідею.

**Фаза 2 — Contextualize (контекстуалізація)** *(використовує `gemma3:4b`)*
Локальний LLM пише 1–2 речення резюме для кожного чанку, описуючи його *у контексті всього документа*. Зберігається у полі payload `context`. Перетворює *«Не повинен перевищувати 512 байт»* на *«Токен сесії в модулі авторизації не повинен перевищувати 512 байт».*

**Фаза 3 — Tag (теґування)** *(використовує `gemma3:4b`)*
Той самий LLM генерує 3–7 семантичних теґів на чанк, пакетно для швидкості. Теґи дозволяють точний фільтрований пошук по всій колекції.

**Фаза 4 — Embed + Upsert (ембедінг та збереження)** *(використовує провайдер ембедінгів)*
`context + text` кодується у:
- **dense** 1024-вимірний вектор (нейронний сенс)
- **sparse** вектор зі змінною розмірністю (лексичні ваги)

Обидва вектори разом із текстом, секцією, теґами, контекстом, source_file і метаданими провайдера зберігаються як одна точка Qdrant.

**Фаза 5 — Link (лінкування)**
Семантичний пошук по всіх колекціях знаходить top-N найбільш схожих чанків для кожного щойно проіндексованого. Двосторонні посилання та зворотні посилання записуються в payload Qdrant і `graph.<collection>.json`, формуючи навігований граф знань.

### Чому локальні моделі?

Жоден текст не виходить за межі вашої машини. Ollama і ONNX працюють повністю локально — важливо для власного коду, внутрішніх специфікацій, клієнтської документації або будь-якого контенту, яким ви не можете ділитися зі стороннім API.

## Система пошуку

### Гібридний пошук (за замовчуванням)

Кожен виклик `qdrant_search` запускає два паралельних запити через Query API Qdrant:

- **Dense leg** — косинусна схожість по 1024-вимірних нейронних векторах
- **Sparse leg** — скалярний добуток по векторах лексичних ваг

Результати об'єднуються через **Reciprocal Rank Fusion (RRF)**. Dense знаходить перефразування та семантичних сусідів; sparse знаходить точні ідентифікатори, env vars, назви функцій і рідкісні технічні терміни. Разом вони надійно обробляють змішані природномовні + технічні запити.

**Dense-only fallback:** колекції, проіндексовані до підтримки sparse, продовжують працювати. `npm run sync` бекфілить sparse вектори для існуючих колекцій.

### Провайдери ембедінгів

| `denseProvider` | `sparseProvider` | Dense-модель | Примітки |
|-----------------|-----------------|--------------|----------|
| `ollama` | `hashed-tf` | `bge-m3`, `snowflake-arctic-embed2`, … | За замовчуванням. Потребує запущеного Ollama. `hashed-tf` — hashed TF encoder (IDF=1) — не справжній BM25, але без залежностей і швидкий. |
| `bge-m3-onnx` | `bge-m3-onnx` | `aapot/bge-m3-onnx` | Задайте `ONNX_EMBED=1`. Завантажує ~2.3 ГБ один раз, кеш у `./models/`. Ollama для ембедінгів не потрібен. Neural sparse — не SPLADE vocabulary expansion, але нейронний і багатомовний. Найкраще для українського / змішаного тексту. |

Провайдер зберігається per-collection у `config.json` і в payload кожної точки. Зміна провайдера викликає автоматичну переіндексацію.

### Налаштування RRF

| Змінна | За замовч. | Ефект |
|--------|-----------|-------|
| `RRF_K` | `60` | Константа згладжування RRF — вищі значення знижують чутливість до позиції в ранжуванні |
| `HYBRID_PREFETCH_LIMIT` | `20` | Кількість кандидатів на кожен leg перед fusion |

## Ранжування результатів (експериментально)

При `RERANK_ENABLED=1` MCP-сервер отримує `top × RERANK_PREFETCH_MULT` кандидатів з Qdrant, оцінює їх локально, а потім повертає найкращі `top` результатів. Вимкнений за замовчуванням; не додає накладних витрат у вимкненому стані.

### Оцінювання

Два етапи: базовий бал `1 / (rank + 1)` з оригінального RRF-рангу, потім детерміновані бусти:

| Сигнал | Буст за замовч. | Примітки |
|--------|----------------|----------|
| токен у `source_file` | 0.08 | Токени запиту в імені файлу чанку |
| токен у `section` | 0.06 | Токени запиту в заголовку секції |
| токен у `tags` | 0.05 | Токени запиту в будь-якому теґу |
| токен у `text` | 0.01 | Токени запиту в тілі чанку (шумний — зменшений) |
| кількість backlinks | 0.04/посилання | Більше вхідних посилань = вищий ранг |

Технічні токени (`snake_case`, `АКРОНІМ`, `camelCase`, довжина ≥ 8) отримують **у 3 рази вищий** бал, ніж прозові слова. Поширені українські та англійські стоп-слова виключені з усіх бустів.

**Жадібний прохід різноманітності** штрафує будь-який чанк із файлу, вже вибраного у результати (незалежно від позиції). **Захист top-1** (`RERANK_PROTECT_TOP1_DELTA=0.05`) запобігає витісненню оригінального RRF rank-0 результату, якщо перевага конкурента не перевищує поріг.

### Результати бенчмарку

Контрольована матриця на одному індексі (21 запит, 4 фікстури, Top-K 5):

| Провайдер | Recall@1 | Recall@5 | MRR |
|-----------|----------|----------|-----|
| `ollama + hashed-tf` | 90% | 100% | 0.938 |
| `ollama + hashed-tf + rerank` | 90% | 100% | 0.938 |
| `bge-m3-onnx` | 95% | 100% | 0.975 |
| `bge-m3-onnx + rerank` | 95% | 100% | 0.975 |

Reranking є **opt-in і нейтральним** на цьому корпусі. Запустіть `npm run bench:retrieval:rerank` на своїх даних перед увімкненням.

### Конфігурація

| Змінна | За замовч. | Опис |
|--------|-----------|------|
| `RERANK_ENABLED` | `0` | `1` для увімкнення rerankінгу в MCP search |
| `RERANK_PREFETCH_MULT` | `4` | Множник кандидатів: отримати `top × N` з Qdrant перед ранжуванням |
| `RERANK_DEBUG` | `0` | `1` для виведення деталей оцінювання в stderr |
| `RERANK_BOOST_SOURCE_FILE` | `0.08` | Буст за збіг токена в `source_file` |
| `RERANK_BOOST_SECTION` | `0.06` | Буст за збіг токена в `section` |
| `RERANK_BOOST_TAGS` | `0.05` | Буст за збіг токена в `tags` |
| `RERANK_BOOST_TEXT` | `0.01` | Буст за збіг токена в `text` |
| `RERANK_BOOST_BACKLINK` | `0.04` | Буст за кожне вхідне backlink-посилання |
| `RERANK_PROTECT_TOP1_DELTA` | `0.05` | Мінімальна перевага балу для витіснення RRF rank-0 |

## Бенчмарк / Якість

semidex постачається з регресійним бенчмарком з 21 запитом по 4 fixture-документах:

```bash
npm run smoke                     # швидкі офлайн тести — Qdrant/Ollama не потрібні
npm run bench:retrieval           # повний бенчмарк пошуку на живому Qdrant
npm run bench:retrieval:compare   # порівняння поряд: ollama vs onnx
npm run bench:retrieval:rerank    # матриця 4 варіантів: ollama±rerank vs onnx±rerank
```

Метрики: `fileRecall@1`, `fileRecall@K`, `MRR`, `nDCG@K`, `sectionHit@K`, `tokenHit@K`, `negativePassRate`, `dupSourceRate`, `sourceDiversity`, `p50`/`p95` latency.

`BENCH_TOP_K=10` змінює глибину пошуку; `BENCH_PROVIDER=onnx` примусово задає провайдер незалежно від `.env`.

Результати зберігаються у `benchmarks/retrieval/results/`. Падіння MRR після зміни коду — сигнал регресії: розберіться перед мержем.

### Sync

```bash
npm run sync
```

Генерує/оновлює `config.json` з реальних колекцій Qdrant, забезпечує наявність необхідних payload-індексів і бекфілить поля `denseProvider`/`sparseProvider` для вже існуючих колекцій. Безпечно запускати повторно; ідемпотентно.

Після sync можна відредагувати `config.json`, щоб задати провайдер або опис для кожної колекції. Дивіться `config.example.json` для всіх полів.

## Відомі обмеження

- **Розмір моделі BGE-M3 ONNX** — ~2.3 ГБ при завантаженні; не завжди практично.
- **`hashed-tf` — не BM25** — IDF=1, без корпусної статистики. Добре для рідкісних технічних токенів; може недооцінювати часті терміни порівняно з BM25/SPLADE.
- **Reranker вимкнений за замовчуванням** — нейтральний на поточному бенчмарк-корпусі; запустіть свою матрицю перед увімкненням.
- **ColBERT не реалізовано** — late-interaction retrieval поки недоступний.
- **Бенчмарк — набір регресійних тестів** — 21 запит по 4 fixture-документах це health check, а не наукова оцінка.
- **Очищення `chunks_out/`** — використовує зіставлення за шаблоном (`base__chunk*.md`). Вручну створені директорії з відповідним іменем призводять до помилки `rmSync`; не впливає на індексацію чи Qdrant.

## Вирішення проблем

**`fetch failed` під час пошуку**
Ollama має бути запущена, коли MCP-сервер обробляє запити — вона ембедить запит у вектор перед зверненням до Qdrant. Запустіть Ollama і перепідключіть MCP-сервер. При `ONNX_EMBED=1` Ollama для пошуку не потрібна.
