# Проблеми колекції `fullstack-python-web` — звіт для Codex

**Колекція:** `fullstack-python-web`
**Джерело:** Private Obsidian learning vault, FullStack Python web development notes
**Дата аудиту:** 2026-06-02
**Файлів:** 45 (теми 1–6), очікується розширення до тем 7+

**Status:** private collection audit, sanitized for repo docs
**Commit safety:** safe to commit — private paths removed
**Recommended action:** normalize source Markdown before reindexing; do not patch core chunker yet

## Проблема 1 — Відсутні підзаголовки `##` / `###`: `section` payload беззмістовний

### Опис

Усі 45 файлів мають лише один `# H1` зверху. Внутрішня структура документа позначена **жирним текстом** на окремому рядку (`**Вставка даних (INSERT)**`, `**Eager і Lazy Loading**`) замість `## / ###` заголовків.

Semidex визначає секції виключно за ATX (`# ## ###`) та Setext (`===` / `---`) заголовками. Жирний текст як псевдо-заголовок не розпізнається.

### Наслідок

- `section` у Qdrant payload = `""` (порожній) або назва `# H1` для всього файлу.
- Усі чанки файлу мають однаковий `section` — корисність payload для орієнтації агента знижена.
- Окремий випадок: chunk починається з рядка ```` ``` ```` → `section: "```"`.
- `qdrant_get_chunk` працює за `collection + source_file + chunk_index` — section не є lookup-ключем і навігація через нього не підтримується MCP.
- Прямий вплив на RRF-ранжування обмежений, але `section` потрапляє в context/tag prompt — порожня або невірна секція може знизити якість LLM-контексту і орієнтацію агента при перегляді результатів.

### Варіанти вирішення

**А. Виправити джерела — рекомендовано для цієї колекції**
Замінити `**Заголовок**` на `## Заголовок` у Obsidian-нотатках вручну або скриптом.
Після збереження — реіндексація автоматична (SHA-256 виявить зміни).
Плюс: покращується також рендеринг в Obsidian; найбезпечніший підхід.
Мінус: ручна робота по 45+ файлах; потрібна обережність щоб не зламати структуру.

**Б. Import normalization step — опційний майбутній інструмент**
Окремий скрипт нормалізації, що запускається перед індексацією і конвертує standalone `**bold**`-рядки у `##` заголовки. Явно обмежений LMS/Obsidian-export артефактами, не змінює production-код.
Плюс: не треба чіпати джерела вручну; повторювана операція для нових файлів.
Мінус: потребує розробки і підтримки окремого інструменту.

**В. Core chunker heuristic — не рекомендовано зараз**
Навчити `parseMarkdown()` розпізнавати standalone `**bold**`-рядки як псевдо-заголовки.
Не рекомендовано: може створити false positives у звичайному Markdown; слід зачекати на skeleton-first chunking design де структурні евристики вирішуватимуться системно.

**Г. Залишити як є**
Section буде порожнім. Основний семантичний retrieval продовжує працювати. Орієнтація агента за секцією недоступна.

## Проблема 2 — Backslash-escaping у коді: точний code search під загрозою

### Опис

У вихідних файлах код усередині ```` ``` ```` блоків містить Markdown-екранування, що є артефактом LMS-експорту:

```
from sqlalchemy import create\_engine, text
result = connection.execute(text("SELECT \* FROM users"))
engine = create\_engine("sqlite:///example\_ex.db", echo\=True)
stmt = select(User).where(and\_(User.fullname.like("%ha%")))
```

Реальний Python-код: `create_engine`, `SELECT * FROM`, `echo=True`, `and_()`.
У chunk.text зберігається: `create\_engine`, `SELECT \* FROM`, `echo\=True`, `and\_()`.

### Масштаб

Зачіпає ~29 файлів з усіх 45 (файли з кодовими блоками, що прийшли з LMS).
Файли без проблеми: `Вступ.md`-файли та кілька теоретичних файлів без коду.

### Наслідок

- Семантичний пошук (`create engine sqlalchemy`) — основний retrieval може продовжувати працювати: dense-вектор обчислюється з LLM-контексту + тексту, і контекст зазвичай правильний.
- Точний лексичний пошук (`create_engine`) — **зона ризику**: sparse-вектор бачить `create\_engine` як один токен, а не `create_engine`. BGE-M3 subword tokenizer частково компенсує, але точний збіг не гарантований.
- Пошук по Python-ідентифікаторах з підкресленням (`mapped_column`, `add_all`, `session.commit`) — потенційно знижений recall. Не верифіковано benchmark.

### Варіанти вирішення

**А. Очистити джерела скриптом — рекомендовано**
PowerShell/Python скрипт: у кожному файлі знайти fenced code блоки ```` ```...``` ````, **тільки всередині них** замінити `\_` → `_`, `\*` → `*`, `\[` → `[`, `\]` → `]`, `\=` → `=`, `\(` → `(`, `\)` → `)`.
Критично: не чіпати escaping поза кодовими блоками — там він може бути легітимним Markdown.
Після збереження — реіндексація автоматична.
Плюс: чисте джерело, правильний код, покращується читання в Obsidian.
Мінус: скрипт потрібно написати акуратно з чіткими межами code fence.

**Б. Import normalization step**
Аналогічна нормалізація як окремий pre-indexing інструмент, не в production indexer.
Плюс: не треба чіпати джерела вручну.
Мінус: потребує розробки окремого інструменту.

**В. Strip escaping у semidex під час chunking — не рекомендовано**
Зміна `src/indexer/phases/chunk.js` — ризик зламати легітимне екранування в інших колекціях.

**Г. Залишити як є**
Прийнятно якщо колекція використовується виключно для концептуального пошуку. Прямий recall по точних Python API (`session.add_all`, `mapped_column`) може бути знижений.

## Проблема 3 — Інлайн-код розбитий на окремі рядки

### Опис

LMS експортує інлайн `code` у Markdown як окремі рядки замість справжнього inline:

```markdown
методу
```
execute()
```
 дозволяє виконувати
```

Замість правильного:
```markdown
методу `execute()` дозволяє виконувати
```

### Наслідок

- У chunk.text між словами з'являються рядки з бектіками.
- Chunker може розрізати речення по цих рядках (бектіки — окремий параграф).
- Читабельність chunk.text знижена.
- Прямий вплив на retrieval обмежений: токени `execute`, `asyncio` тощо знаходяться. Chunking по помилкових межах може дробити контекст — не верифіковано.

### Варіанти вирішення

**А. Нормалізувати джерела скриптом**
Знайти патерн: рядок із лише ```` ``` ```` (без мовного тега), де попередній і наступний рядки — не порожні → склеїти в інлайн `` `code` ``.
Плюс: чистий Markdown, правильний рендеринг в Obsidian.
Мінус: складний regex, ризик зачепити справжні блокові ```` ``` ````.

**Б. Import normalization step**
Аналогічна нормалізація як pre-indexing інструмент.

**В. Залишити як є — прийнятно**
Прямий вплив на retrieval не підтверджений benchmark. Читабельність chunk.text знижена, але це внутрішній артефакт.

## Проблема 4 — `Вступ.md` файли (1 chunk, практично не виходять у топ)

### Опис

Кожна тема містить `1. Вступ.md` (~15–20 рядків загального опису). Після chunking → 1 chunk без конкретних технічних термінів. Рідко виходить у rank-1.

### Наслідок

- Слабкі чанки у колекції.
- На якість пошуку для конкретних запитів прямий вплив обмежений.
- Корисні лише для запитів типу «що охоплює тема 4?».

### Варіанти вирішення

**А. Залишити як є** — вступи несуть мета-інформацію, корисну для загальних запитів.

**Б. Додати до `.semidexignore`** — якщо вступи не несуть пошукової цінності для даної колекції.

## Проблема 5 — Нестандартні мовні теги кодових блоків

### Опис

LMS використовує нестандартні теги підсвітки синтаксису: `routeros`, `livecodeserver`, `taggerscript`, `n1ql`, `isbl`, `stylus`, `lasso`. Вони потрапляють у перший рядок кодового блоку в chunk.text.

### Наслідок

- Мовний тег — шум у тексті (мінімальна семантична вага).
- Прямий вплив на retrieval обмежений.
- Читабельність chunk.text незначно знижена.

### Варіанти вирішення

**А. Залишити як є** — прямий вплив на retrieval не підтверджений.

**Б. Strip мовних тегів в import normalizer** — замінювати невідомі теги на ```` ``` ```` без тега або на `python` як частина pre-indexing нормалізації.

## Технічні деталі для Codex

**Де визначаються секції в semidex:**
`src/indexer/phases/chunk.js` → функція `parseMarkdown()` → рядки 142–189
Розпізнає: `^(#{1,6}) (.+)` та Setext `===` / `---`.
**Не розпізнає:** `**bold**` на окремому рядку.

**MCP retrieval API:**
`qdrant_get_chunk(collection, source_file, chunk_index, window)` — section є payload для орієнтації, не lookup-ключ.
`qdrant_search` — гібридний RRF; section не є окремим полем фільтрації.

**Де читаються файли:**
`src/indexer/phases/chunk.js:418` → `readFileSync(filePath, 'utf8')`

**Патерн backslash escaping у джерелах:**
Присутній **виключно у середині кодових блоків** (між ```` ``` ```` і ```` ``` ````).
Поза кодовими блоками — не виявлено. Скрипт очищення має суворо дотримуватись цієї межі.

**Патерн розбитого інлайн-коду:**
```
(будь-який текст)\n```\n(ідентифікатор без пробілів)\n```\n(будь-який текст)
```

**Кількість файлів з backslash escaping:** ~29 з 45.
**Кількість файлів без `##` заголовків:** 45 з 45.
